# Как мы работаем

Памятка: что сказать Claude и что запустить самому. Подробности — в скиллах `.claude/skills/` и в README.

## Цикл задачи

| Шаг       | Что сказать                                         | Что происходит                                                                                    |
|-----------|-----------------------------------------------------|---------------------------------------------------------------------------------------------------|
| Груминг   | «давай погрумим …», «обсудим задачу …», «заведи задачу …» | Скилл `groom`: проблема → концепция → решения по одному → для задачи с форматом — модель целиком → черновик задачи (для компонента и пресета — по заготовке) → после «ок» задача на доске в Groomed → самопроверка; холодное чтение — с вашего согласия. Новый компонент с пресетами или несколькими подзадачами — эпик: эпик → подзадачи → задача «Пресеты `<Компонент>`: какие нужны» → номера в таблицу эпика |
| Сброс     | `/clear`                                            | После груминга                                                                                    |
| Работа    | «берём в работу #N»                                 | Скилл `take`: сверка строки в таблице эпика, ветка `task/<N>-…` от `origin/dev`, In progress, изменения и запись в журнал, проверка |
| Figma     | открыть плагин, отрисовать, сказать «отрисовал»     | Claude проверяет через MCP структуру, потом скриншоты; затем смотрите вы                          |
| Коммит    | «коммить»                                           | Только после вашего согласия; затем PR в `dev`, In review                                         |
| Слияние   | сливаете сами (squash), говорите «слил»             | Claude делает `git fetch origin`; для подзадачи эпика — сверяет таблицу эпика, после последней — критерий пресетов |
| Сброс     | `/clear`                                            | После PR                                                                                          |

Посреди работы не сбрасываем: договорённости, не записанные в задачу или память, теряются.

## Полезные слова

- **«закругляемся»** — Claude записывает незаписанное: решения в задачу, план в заметку своей линии работы в памяти —
  и одной строкой говорит, где что лежит. Говорите перед `/clear` или перед уходом.
- **Новая сессия** — `groom` и `take` первым шагом читают заметку своей линии работы, состояние ветки и задачу с
  комментариями; если ветка задачи уже есть, работа продолжается в ней. Тело задачи — действующее решение,
  комментарии — история: при расхождении действует тело.
- **Проектирование контракта** — скилл `contract-authoring`: API атомов, типов и компонентов, пресеты, JSON-контракты
  и описания пресетов по спецификации. Его используют `groom` и `take`.
- **Эпик компонента** — таблица «Подзадачи» («Задача | Что даёт | Зависит от») без отметок статуса: состояние
  показывает список подзадач эпика на GitHub. Пресет входит в эпик компонента, на котором стоит его корень (пресет на
  пресете — в эпик компонента под корневым пресетом). Эпик готов, когда задачи на пресеты закрыты — сделаны или
  отклонены с причиной.
- Темы, всплывшие по ходу, Claude предлагает завести отдельно в Backlog — сами в задачу не попадают.
- **Холодное чтение** — после груминга Claude может предложить проверить задачу агентом, который видит только её
  тело: что ему непонятно, то и дописывается в задачу. Запускается только с вашего согласия. Если после правок
  изменились модель, формат или разбивка на PR, Claude предложит второе чтение.

## Параллельная работа

Вторая линия работы идёт в отдельной папке `git worktree`, а не во втором клоне: память Claude общая на все папки
репозитория, коммиты видны сразу.

```sh
git worktree add ../<папка> origin/dev        # папка второй линии
```

- Одна ветка — одна папка: Git не открывает ветку в двух папках сразу. Поэтому `dev` не открывается для работы ни в
  одной из папок: ветка задачи создаётся от `origin/dev`, после слияния — `git fetch origin`.
- У каждой линии своя заметка в памяти Claude: у основной — «текущая работа», у второй — своя. `groom` и `take` читают
  и пишут заметку той линии, в папке которой запущена сессия.

## Доска

[UI Design System](https://github.com/users/Nakulov/projects/8): Backlog → Groomed → In progress → In review → Done.

```sh
tools/board.sh status <N> groomed              # backlog, groomed, in-progress, in-review, done
tools/board.sh issue "<заголовок>" <метка> body.md   # печатает номер
tools/board.sh sub <эпик> <N>
```

Метки: `component`, `foundation`, `spec`, `process`, `epic`. Этапы — вехи из `ROADMAP.md`.

## Команды репозитория

```sh
python3 -m pip install -r tools/requirements.txt   # один раз
python3 tools/sync.py                              # после правки контрактов и образцов: min/max, README, IDE
python3 tools/validate.py --base origin/dev        # проверка, как в PR
python3 tools/validate_model.py <файл>             # проверить одну модель по контракту
python3 tools/bundle.py                            # набор для плагина из ветки задачи: build/bundle.json
cd figma-plugin && npm ci && npm run build         # плагин: dist/
```

## Проверка в Figma

1. Figma Desktop → **Plugins → Development → UI Design System** (первый раз: Import plugin from manifest… →
   `figma-plugin/manifest.json`).
2. Загрузить набор: «Загрузить с GitHub» — набор из `dev` (публикуется CI после merge; Pages кэширует до 10 минут,
   какой коммит загружен — в строке «Источник»); «Открыть файл…» → `build/bundle.json` — ветка задачи до merge.
   Затем «Построить foundation» → «Отрисовать образцы»; для проверки импорта и обновления
   макетов — «Построить компоненты» → «Отрисовать экраны».
3. Сказать Claude «отрисовал»; после его проверки — посмотреть самим и подтвердить.
