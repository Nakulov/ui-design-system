# Документация в Figma

**Статус:** Черновик для согласования  
**Версия:** 0.13

## 1. Назначение

Документ описывает архитектуру генерации, оформления и сопровождения документации публичных сущностей — компонентов и foundation-сущностей — в Figma. Он не определяет публичный API компонентов и не зависит от конкретной реализации Android или iOS.

## 2. Источники и ответственность

| Слой | Ответственность |
|---|---|
| UI Contract | Состав компонента, свойства, варианты, доступность на платформах (`releaseVersions`). |
| Documentation Manifest | Утверждённое содержание документации: секции, примеры, сценарии, выбранные композиции. |
| Documentation UI Library | Элементы оформления документации — шаблоны-модели наших компонентов (раздел 5). |
| Figma Generation Skill | Анализ контрактов, проектирование Figma-компонентов (`figma-mapping.md`), предложение секций и примеров, подготовка/обновление манифеста после согласования. |
| Figma Plugin | Детерминированное построение и синхронизация объектов Figma: Figma-компонентов и переменных по `figma-mapping.md`, документации — из манифеста и библиотеки оформления. |

Манифест не описывает низкоуровневое дерево Figma-слоёв и не содержит Figma node IDs. Источник истины для документации — файлы в Git, а не вручную изменённые сгенерированные объекты.

## 3. Организация страницы

Для каждой документируемой сущности предусмотрена отдельная страница Figma, названная по имени контракта, с
областями плагина:

```text
Page: Badge
├── Release Checklist          ← слева
└── Generated Documentation
```

- **Generated Documentation** полностью контролируется плагином. Ручные правки внутри этой области могут быть перезаписаны.
- **Release Checklist** — чеклист готовности к релизу в Figma (раздел 3.5).

Места для ручной документации в файле библиотеки нет: источник истины — Git, а свою документацию продукт ведёт в своих
файлах. Другие узлы страницы плагин не трогает: прежние фреймы Custom Documentation остаются на месте.

Figma-компоненты лежат на странице `Components` (`figma-mapping.md`, раздел 3.2, правило 6) и живут отдельно от
документации. Документация использует их экземпляры, а не независимые визуальные копии. Синхронизация документации не
удаляет и не пересоздаёт Figma-компоненты.

Исключение — символы (`Icon`): они отображаются в компоненты `icon/<имя>` (`figma-mapping.md`, раздел 3.1, правило 12),
и эти компоненты лежат на странице `Icon` рядом с документацией в области Component.

Страница и её области хранят в `sharedPluginData` (`uiContracts`, ключ `ref`) идентификатор сущности (`figma-mapping.md`, раздел 7.1); области хранят ключ `role`: `generated`, `checklist` и, у `Icon`, `component`.

### 3.1. Страницы foundation

Страница foundation-сущности строится по правилу, без манифеста: выбирать в ней нечего (`documentation-manifest.md`, раздел 4.2).

1. **Overview** — элементы `heading` с `name` и `description` с `description` публичного контракта.
2. **Values** — секция с таблицей строк `valueRow` по вариантам файла значений темы `default` в его порядке: имя варианта, величина и превью (раздел 5). Величина по режимам записывается через « / », одинаковые — один раз: цвет — шестнадцатеричный код, роль типографики — «размер / интервал · вес», тень — «y · blur».
3. **Usage** — раздел README «Рекомендации по использованию», переведённый в модели (`documentation-manifest.md`, раздел 4.1). Пустой раздел не выводится.
4. **History** — последняя секция: таблица строк `historyRow` по записям журнала `changelog.json` сущности в его
   порядке, от новых к старым (`schema-format.md`, раздел 11.4):
   - дата — `date`, при наличии `issue` — « · #N»: «2026-11-02 · #97»;
   - вид — `kind` словом: «Добавлено», «Изменено», «Удалено», «Переименовано»;
   - цель — `target`, без него «—», у `renamed` — «`from` → `target`»;
   - описание — `description` фрагментами по подмножеству Markdown (`schema-format.md`, раздел 11.2).

### 3.2. Описание системы и порядок страниц

Страница `Overview` (`role` — `overview`) описывает систему для потребителя. Текст — файл `docs/overview.md`: разделы второго уровня (`##`) становятся элементами `section`, текст разделов записан подмножеством Markdown (`schema-format.md`, раздел 11.2) и проверяется валидатором. Под текстом плагин добавляет секции `Foundation`, `Core` и `Components` — списки страниц foundation, core и
компонентов с описаниями из контрактов.

Порядок страниц: `Overview`, разделитель `——— Foundation ———`, страницы foundation по алфавиту, разделитель `——— Core ———`, страницы core по алфавиту, разделитель `——— Components ———`, страницы компонентов по алфавиту, разделитель `——— Library ———`, `Components`, `Samples`. Разделители — пустые страницы с `role` `separator:foundation`, `separator:core`, `separator:components` и `separator:library`. Остальные страницы файла остаются после них.

Область Generated Documentation стоит в начале координат страницы, а если на странице есть другие узлы — слева от них:
на странице символов (`Icon`) — слева от компонентов `icon/<имя>`. Release Checklist стоит слева от Generated
Documentation: `Release Checklist` | Generated Documentation | компоненты `icon/<имя>`.

### 3.3. Страницы core

Страница сущности core строится по манифесту `docs.json` (`documentation-manifest.md`, разделы 2, 4.2, 5.2) и
есть у каждой сущности core, доступной в Figma. Секции выводятся в порядке манифеста:

1. **Overview** — `heading` с `name` и `description` с `description` контракта.
2. **Properties** — таблица строк `propertyRow`: у объекта — поля, у `oneOf` — варианты. Тип — имя контракта по `$ref`
   (у массива — с `[]`) или примитивный тип. Описание поля — его `description`; у элемента `oneOf` своего описания нет, и
   выводится описание вспомогательного определения сущности, а у общего типа (`Spacing` у `padding.all`) — «—». Платформы — выпущенные (`released`) по итоговому статусу `releaseVersions`
   через « · »; если не выпущено нигде — «не выпущено». У Android и iOS после имени — итоговая версия, если она указана: у
   уровня или у ближайшего предка (`schema-format`, §8.5); например, «Android 1.5 · iOS · Figma».
3. **Variants, States, Layout Behavior** — `grid` из элементов `example`: превью — демонстрация, подпись — `caption`
   примера.
4. **Usage** — как у foundation (раздел 3.1).
5. **Platform Support** — таблица строк `releaseRow` по платформам в порядке `schema-format.md`, раздел 8.1: Android,
   iOS, Figma. Строки строятся из итоговых статусов `releaseVersions` (`schema-format.md`, раздел 8.5) публичного
   контракта и уровней, к которым ведут пути `target` журнала (`schema-format.md`, раздел 11.4, правило 2): свойств,
   элементов `oneOf`, в том числе развёрнутых, и значений, в том числе из вспомогательных определений. Поля `Component`
   не входят.
   - Первая строка платформы — сам контракт: платформа, версия и имя контракта.
   - Ниже — уровни, выпущенные с более поздней версией: итоговая версия уровня больше итоговой версии его родителя
     (у родителя без версии — любая). Наследники с той же версией не выводятся. Уровни сгруппированы по версии,
     версии — по возрастанию; платформа указана только в первой строке.
   - Версия — число; «✓», если уровень выпущен без версии (у Figma так всегда); «—», если контракт не выпущен.
   - Цели — пути через запятую в формате `target` журнала: `truncation`, `truncation.start`; у контракта — его имя;
     у невыпущенного контракта — «не выпущено».
   - Невыпущенные и исключённые уровни не выводятся: их статусы видны в Properties.

   Например, Text выпущен на Android в 1.0, `truncation` — в 1.5, на iOS не выпущен, в Figma выпущен:

   | Платформа | Версия | Цели         |
   |-----------|--------|--------------|
   | Android   | 1.0    | Text         |
   |           | 1.5    | truncation   |
   | iOS       | —      | не выпущено  |
   | Figma     | ✓      | Text         |
6. **History** — как у foundation (раздел 3.1); в манифесте — последней секцией.

### 3.4. Страницы компонентов

Страница компонента строится по манифесту `docs.json` (`documentation-manifest.md`, разделы 2, 4.2, 5.1) и есть у
каждого публичного компонента, доступного в Figma. Секции выводятся в порядке манифеста:

1. **Overview** — `heading` с `name`, `description` с `description` контракта и `grid` с одним элементом `example`:
   превью — образец основного примера, подпись — `caption`.
2. **Properties** — таблица строк `propertyRow` собственных свойств компонента, как у core (раздел 3.3), и последней
   строкой `Component`: тип — `Component`, описание — «Базовая модель: » и поля `Component` через запятую, у
   `appearance` — контексты `appearanceContext` в скобках; платформы — по `releaseVersions` контракта `Component`.
3. **Variants** — `grid` из элементов `example`: превью — образец из `samples/`, подпись — `caption`.
4. **Usage** — как у foundation (раздел 3.1).
5. **Platform Support** — как у core (раздел 3.3).
6. **History** — как у foundation (раздел 3.1); в манифесте — последней секцией.

Пример, у корня которого ширина `fill`, рисуется элементом `exampleWide` — карточкой фиксированной ширины, как на
странице `Samples`: в карточке `example` по содержимому ширину такого примера задала бы подпись. Образцы
рисуются ядром отрисовки: компоненты — экземплярами Figma-компонентов библиотеки (`figma-mapping.md`,
раздел 10), поэтому страница компонента строится после библиотеки. Картинки по адресу Figma не загружает и показывает
вместо них заглушку.

### 3.5. Release Checklist

Фрейм `Release Checklist` показывает чеклист готовности к релизу в Figma (`figma-mapping.md`, раздел 8) рядом с
документацией сущности.

```text
Release Checklist
Figma: notReleased · авто 4/5 · ручные 2/10
Отметки на сборке f12028c · 2026-10-27

Автоматические
 ✓  1  validate.py проходит на сборке импорта
 ✗  3  Вид, свойства, variant и режимы соответствуют контракту
Ручные
 ✓  6  Variant Component Set … правильны в светлой теме
 —  7  То же в тёмной теме
```

1. **Где.** На странице компонента с `figma.json`, кроме `Container`, — полный чеклист (`figma-mapping.md`, раздел 8.2);
   на страницах foundation, core и `Container` — сокращённый (раздел 8.3). На `Overview` фрейма нет.
2. **Пункты** берутся из набора (`bundle-format.md`, раздел 3.12): номер, вид, текст и к чему пункт применим. Текст
   выводится фрагментами по подмножеству Markdown (`schema-format.md`, раздел 11.2).
3. **Сборка.** Фрейм — модель элементов оформления (раздел 5): `page`, `heading`, `description`, `section` и
   `checklistRow`; строится по правилу, без манифеста. Первая строка под заголовком — статус `figma` контракта и число
   отмеченных пунктов каждого вида.
4. **Автоматические пункты** плагин отмечает при каждой сборке документации: ✓ — пройдено, ✗ — нет; причину ✗ он
   пишет предупреждением в отчёт. Сборки сущности — `foundation` у foundation, `foundation` и `components` у core и
   компонентов, в том числе `Container` (`figma-mapping.md`, раздел 7, правило 11).

   | № | ✓, если                                                                                                                                                                                                                                                         |
   |---|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
   | 1 | Сборки сущности сделаны без незакоммиченных изменений (`dirty: false`): набор с ошибками `validate.py` не собирается.                                                                                                                                           |
   | 2 | Метки сборок сущности совпадают с открытым набором («совпадает»).                                                                                                                                                                                               |
   | 3 | Компонент: на странице `Components` есть Component или Component Set нужного вида, имена и значения variant-свойств, включая `state`, совпадают с `figma.json`. Foundation: коллекция сущности с режимами файла значений и переменными всех вариантов, у `Icon` — компоненты всех символов. |
   | 4 | В Figma-компоненте заливки и обводки, ненулевые отступы, промежутки, скругления и толщины обводки привязаны к переменным, у текстов назначен стиль. Вложенные экземпляры не проверяются: у них свой чеклист.                                                     |
   | 5 | Generated Documentation нарисована без предупреждений, в манифесте есть обязательные секции (`documentation-manifest.md`, раздел 4.2).                                                                                                                         |
5. **Ручные пункты** отмечаются в окне плагина: для открытой страницы — список ручных пунктов с переключателями и
   кнопка «Сбросить отметки». Отметка — текст ✓ или —: компонента `Checkbox` в системе нет. Отметки хранятся в
   `sharedPluginData` фрейма (`uiContracts`, ключ `checks`) и переживают сборку; после переключения плагин
   перерисовывает фрейм. Окно отмечает пункты только с открытым набором: тексты пунктов — в нём.
6. **Сборка отметки.** Каждая отметка хранит сборку документации в файле, на которой её поставили: `commit` и
   `committedAt`. Фрейм показывает самую старую — «Отметки на сборке f12028c · 2026-10-27»; если она не совпадает с
   текущей сборкой документации, строка выделена цветом `error`. Без отметок — «Отметок нет». Сами отметки при новой
   сборке не сбрасываются: плагин не отличает правку описания от ломающей (`figma-mapping.md`, раздел 8.4).
7. **Статус** `figma` фрейм берёт из контракта. Отметки статус не меняют: `released` проставляется в репозитории через PR
   (`figma-mapping.md`, раздел 8.1).
8. Результаты автоматических пунктов хранятся в том же фрейме (ключ `auto`), чтобы перерисовка после отметки не
   повторяла проверки.

## 4. Модульная документация

Skill выбирает необходимые секции исходя из контракта и особенностей компонента. Необязательные секции не создаются только ради единообразия.

Базовая библиотека типов секций:

| Секция | Назначение |
|---|---|
| Overview | Название, описание из контракта и, для компонентов, основной пример. |
| Values | Шкала значений foundation-сущности: переменные Figma, величины по режимам, превью величин. |
| Anatomy | Визуальная схема устройства компонента с выносками. |
| Properties | Свойства, типы, значения, описания и доступность платформ. |
| Variants | Репрезентативные комбинации свойств. |
| States | Визуальные состояния и, опционально, интерактивный прототип Figma. |
| Edge Cases | Граничные сценарии, обнаруженные автоматически или заданные явно. |
| Layout Behavior | Поведение при изменении размеров контейнера и ограничений компоновки. |
| Usage | Текстовые рекомендации из README и визуальные Do / Don't. |
| Platform Support | Выпуски по платформам из `releaseVersions`; на страницах компонентов и core, перед History. |
| History | Журнал изменений API из `changelog.json`; на каждой странице, последней. |

Перечень расширяемый; его наличие не означает, что каждая секция обязательна. Применимость секций к компонентам и foundation-сущностям определяет `documentation-manifest.md`, раздел 4.2.

## 5. Библиотека оформления документации

Документация оформлена **компонентами самой дизайн-системы**: элементы страниц — модели `Container`, `Text` и других
компонентов, их рисует ядро отрисовки плагина (`figma-mapping.md`, раздел 10). Документация показывает систему её же
средствами, в том числе в тёмной теме, и проверяет библиотеку.

Оформление документации — тема `default`. Независимый от продукта стиль появится темой `documentation` — своими
величинами тех же ролей (`ColorRole`, `TypographyRole`, `Spacing` и других), когда в Figma появятся темы помимо
`default` (`figma-mapping.md`, раздел 12). Отдельные контракты токенов документации не используются.

Элементы оформления — общие шаблоны — лежат в `figma/documentation/elements/<имя>.json`. Превью величин foundation и
демонстрации core лежат в своей сущности (`schema-format.md`, раздел 11.1): `contracts/foundation/<сущность>/preview.json`
и `contracts/core/<сущность>/demos/<имя>.json` (`documentation-manifest.md`, раздел 5.2). Демонстрация — элемент
без дырок (`holes` пустой). Элемент — **шаблон-модель с дырками**: вид
(роли, отступы, цвета) записан данными, а сборку страницы — какие элементы, какие строки и откуда величины — выполняет
плагин по манифесту (`documentation-manifest.md`).

```json
{
  "holes": {
    "title": { "kind": "text", "sample": "Values" },
    "content": { "kind": "items", "sample": [ { "Text": { … } } ] }
  },
  "model": {
    "Container": { …, "children": [ { "Text": { …, "content": { "plain": "$title" } } }, "$content" ] }
  }
}
```

1. `holes` — дырки элемента: имя → вид и `sample`. `model` — модель компонента (`schema-format.md`, раздел 4.5), в
   которой строка `"$имя"` обозначает дырку.
2. Виды дырок: `text` — строка, `spans` — фрагменты `Text` (`rich`), `component` — одна модель, `items` — список
   моделей. Дырка `items` внутри массива разворачивается в его элементы.
3. `sample` — значение дырки для проверки. Каждая дырка объявлена и используется; модель с подставленными `sample` корректна.
   Это проверяет валидатор (`schema-format.md`, раздел 12).
4. Плагин рисует каждый элемент, превью и демонстрацию с подставленными `sample` на странице Samples в строке
   `Documentation`; превью и демонстрации подписаны с каталогом сущности: `Documentation#spacing/preview`,
   `Documentation#layout/widthSizing`.
5. Формат файла канонический, как у образцов (`schema-format.md`, раздел 11.1).

Набор элементов:

| Элемент                  | Дырки                                              | Где используется                         |
|--------------------------|----------------------------------------------------|------------------------------------------|
| `page`                   | `sections`                                         | корень страницы документации             |
| `section`                | `title`, `content`                                 | каждая секция                            |
| `heading`, `description` | `text`                                             | Overview                                 |
| `paragraph`, `listItem`  | `text` (фрагменты), `marker`                       | Usage (`documentation-manifest.md`, 4.1) |
| `table`, `propertyRow`   | `rows`; `name`, `type`, `description`, `platforms` | Properties                               |
| `valueRow`               | `name`, `value`, `sample`                          | Values у foundation-сущностей            |
| `grid`, `example`        | `items`; `preview`, `caption`                      | Variants, States, примеры                |
| `exampleWide`            | `preview`, `caption`                               | примеры шириной `fill`                   |
| `releaseRow`             | `platform`, `version`, `targets`                   | Platform Support                        |
| `historyRow`             | `date`, `kind`, `target`, `description` (фрагменты) | History                                 |
| `checklistRow`           | `mark`, `number`, `text` (фрагменты)               | Release Checklist (раздел 3.5)          |

Строки таблицы разделяются отступами и фоном строки: разделителя в системе пока нет. Набор расширяется: `notice`,
Anatomy с выносками, Do / Don't.

**Превью величин** — шаблоны того же формата с одной дыркой `value` — именем варианта. Превью есть у каждой публичной
foundation-сущности с файлом значений; это проверяет валидатор.

| Сущность         | Превью                                                                                                     |
|------------------|------------------------------------------------------------------------------------------------------------|
| `Spacing`        | `Container` высотой `xs` с отступом слева `$value` и фоном `primary`                                       |
| `Size`           | `Container` `fixed $value × $value`, фон `primary`                                                         |
| `ColorRole`      | `Container` `s × s`, фон `$value`, обводка `outline`                                                       |
| `CornerRadius`   | `Container` `xl × xl`, фон `surface2`, скругление `$value`                                                 |
| `BorderWidth`    | `Container` `xl × xl`, обводка `$value` цветом `outlineStrong`                                             |
| `Elevation`      | `Container` `xl2 × xl`, фон `surface`, тень `$value`                                                       |
| `TypographyRole` | `Text` «Съешь же ещё этих мягких булок» ролью `$value`, на оставшуюся ширину в одну строку (`maxLines: 1`) |
| `Icon`           | `Image` с символом `$value`                                                                                |

Геометрия адаптивна, но не произвольна: Skill выбирает из утверждённых элементов, плагин не принимает свободные
инструкции AI по созданию произвольного дерева слоёв.

## 6. Примеры

- В документации показываются **репрезентативные комбинации**, а не обязательное декартово произведение всех свойств. При необходимости допускается полная матрица.
- Наличие примера в документации не определяет набор variant Figma-компонента; это разные задачи.
- Для нескольких тем поддерживаются сравнительные композиции и отдельные тематические блоки. Skill выбирает наиболее читаемую форму.
- Примеры компонентов — образцы из `samples/`, демонстрации core — модели из `demos/` сущности (`documentation-manifest.md`, раздел 5).
- Edge Cases выводятся из типов и ограничений контракта и дополняются явно заданными сценариями, которые хранятся вне публичного контракта.
- Layout Behavior демонстрируется реальными механизмами Figma Auto Layout/Constraints, а не картинками.
- Интерактивные прототипы Figma необязательны и могут появиться на следующем этапе реализации.

## 7. Документирование платформ и поведения

- Доступность Android, iOS и Figma отображается рядом с соответствующими свойствами на основе `releaseVersions`, а выпуски по версиям — в секции Platform Support (раздел 3.3).
- Anatomy в первой версии — статическая визуальная схема с выносками. Стабильные идентификаторы частей могут в будущем позволить связать выноски с реальными слоями.
- Usage может содержать визуальные Do / Don't и текстовые рекомендации. Текстовые рекомендации берутся из раздела README «Рекомендации по использованию» (`documentation-manifest.md`, раздел 4.1). Рекомендации, не следующие напрямую из контракта, требуют утверждения перед фиксацией в README.

## 8. Генерация и синхронизация

```text
UI Contracts + правила документации + samples
                     ↓
          Figma Generation Skill
                     ↓
      Documentation Manifest (Git)
                     ↓
       Validator → Figma Plugin
                     ↓
       Generated Documentation
```

Манифест хранит стабильные логические идентификаторы секций и примеров. Целевая модель — **инкрементальное обновление** по этим идентификаторам. На первом этапе допускается полная пересборка Generated Documentation и Release Checklist (без ручных отметок), но не Figma-компонента.

Объекты Generated Documentation (области, секции, примеры) связываются с манифестом так же, как Figma-компоненты с контрактами (`figma-mapping.md`, раздел 7.1): в `sharedPluginData` в пространстве имён `uiContracts` хранится путь к манифесту от корня репозитория и `id` секции или примера. Имена объектов идентификаторами не являются.

Синхронизация не сохраняет ручные правки внутри областей плагина; смешивать ручные и генерируемые изменения автоматически не планируется. Ручные отметки чеклиста — данные фрейма, а не правки слоёв (раздел 3.5).

## 9. Проверка и согласование

- Skill предлагает состав секций, композиции, примеры и рекомендации; решения утверждаются перед сохранением.
- Независимый от Figma валидатор проверяет формат манифеста, ссылки на контракты, примеры и демонстрации (`documentation-manifest.md`, раздел 8). Плагин дополнительно проверяет данные при загрузке.
- Спецификация Documentation Manifest версионируется отдельно от спецификации UI-контрактов. Текущие версии всех спецификаций указаны в `spec-versions.json` в корне репозитория (`schema-format.md`, раздел 11.3).

## 10. Не определено на этом этапе

- Алгоритм инкрементального обновления Generated Documentation по идентификаторам.
- Правила генерации интерактивных прототипов.
- Локализация документации (в первой версии тексты встроены в манифест, контракты и README).
