# Документация в Figma

**Статус:** Черновик для согласования  
**Версия:** 0.1

## 1. Назначение

Документ описывает архитектуру генерации, оформления и сопровождения документации публичных сущностей — компонентов и foundation-сущностей — в Figma. Он не определяет публичный API компонентов и не зависит от конкретной реализации Android или iOS.

## 2. Источники и ответственность

| Слой | Ответственность |
|---|---|
| UI Contract | Состав компонента, свойства, варианты, доступность на платформах (`releaseVersions`). |
| Documentation Manifest | Утверждённое содержание документации: секции, примеры, сценарии, выбранные композиции. |
| Documentation UI Library | Независимый стиль документации: токены, композиционные шаблоны, элементы оформления. |
| Figma Generation Skill | Анализ контрактов, проектирование Component Set (`figma-mapping.md`), предложение секций и примеров, подготовка/обновление манифеста после согласования. |
| Figma Plugin | Детерминированное построение и синхронизация объектов Figma: Component Set и переменных по `figma-mapping.md`, документации — из манифеста и библиотеки оформления. |

Манифест не описывает низкоуровневое дерево Figma-слоёв и не содержит Figma node IDs. Источник истины для документации — файлы в Git, а не вручную изменённые сгенерированные объекты.

## 3. Организация страницы

Для каждого документируемого компонента предусмотрена отдельная страница Figma, названная по имени контракта, с тремя независимыми областями:

```text
Page: Button
├── Generated Documentation
├── Custom Documentation
└── Component Set
```

- **Generated Documentation** полностью контролируется плагином. Ручные правки внутри этой области могут быть перезаписаны.
- **Custom Documentation** предназначена для ручных дополнений и не затрагивается синхронизацией.
- **Component Set** существует отдельно от документации и управляется отдельным жизненным циклом (`figma-mapping.md`). Документация ссылается на реальные компоненты и использует их instances, а не независимые визуальные копии.

Синхронизация документации не должна удалять или пересоздавать Component Set.

Страница foundation-сущности содержит только Generated Documentation и Custom Documentation: такие сущности представлены в Figma переменными, а не Component Set (`figma-mapping.md`, раздел 3.1).

## 4. Модульная документация

Skill выбирает необходимые секции исходя из контракта и особенностей компонента. Необязательные секции не создаются только ради единообразия.

Базовая библиотека типов секций:

| Секция | Назначение |
|---|---|
| Overview | Название, описание из контракта и, для компонентов, основной пример. |
| Values | Шкала значений foundation-сущности: переменные Figma, величины по режимам, образцы. |
| Anatomy | Визуальная схема устройства компонента с выносками. |
| Properties | Свойства, типы, значения, описания и доступность платформ. |
| Variants | Репрезентативные комбинации свойств. |
| States | Визуальные состояния и, опционально, интерактивная демонстрация. |
| Edge Cases | Граничные сценарии, обнаруженные автоматически или заданные явно. |
| Layout Behavior | Поведение при изменении размеров контейнера и ограничений компоновки. |
| Usage | Текстовые рекомендации из README и визуальные Do / Don't. |
| Platform Support | Необязательная сводка по платформам для сложных компонентов. |

Перечень расширяемый; его наличие не означает, что каждая секция обязательна. Применимость секций к компонентам и foundation-сущностям определяет `documentation-manifest.md`, раздел 4.2.

## 5. Библиотека оформления документации

Документация имеет **собственный визуальный стиль**, независимый от брендбука демонстрируемых компонентов. Light и Dark варианты компонента могут находиться рядом в одном оформлении документации.

Внешний вид строится из переиспользуемых элементов, например: `Section`, `Heading`, `Description`, `PropertyTable`, `PreviewGrid`, `PreviewRow`, `StateMatrix`, `ExampleCard`, `Notice`.

Геометрия адаптивна, но не произвольна: Skill выбирает из утверждённых композиций; размеры, отступы, типографику, Auto Layout и ограничения определяет Documentation UI Library. Плагин не принимает свободные инструкции AI по созданию произвольного дерева слоёв.

Расположение правил в репозитории:

```text
figma/documentation/
├── tokens/
│   └── spacing/
│       ├── Spacing.json
│       └── Spacing.values.json
├── layouts/
└── sections/
```

**Токены** описываются теми же средствами, что и foundation-сущности дизайн-системы: контрактом и файлом значений (`schema-format.md`, разделы 9 и 11). Контракты токенов принадлежат библиотеке оформления и не зависят от контрактов дизайн-системы: изменение, например, шкалы отступов дизайн-системы не затрагивает документацию. В Figma токены становятся отдельными коллекциями переменных (`figma-mapping.md`, раздел 3.1).

Формат `layouts/` и `sections/` ещё не согласован.

## 6. Демонстрационные примеры

- В документации показываются **репрезентативные комбинации**, а не обязательное декартово произведение всех свойств. При необходимости допускается полная матрица.
- Наличие примера в документации не определяет набор вариантов в Component Set; это разные задачи.
- Для нескольких тем поддерживаются сравнительные композиции и отдельные тематические блоки. Skill выбирает наиболее читаемую форму.
- Демонстрации могут использовать значения свойств прямо в манифесте либо именованные fixtures.
- Edge Cases выводятся из типов и ограничений контракта и дополняются явно заданными сценариями, которые хранятся вне публичного контракта.
- Layout Behavior демонстрируется реальными механизмами Figma Auto Layout/Constraints, а не картинками.
- Интерактивные примеры Figma Prototype необязательны и могут появиться на следующем этапе реализации.

## 7. Документирование платформ и поведения

- Доступность Android, iOS и Figma отображается рядом с соответствующими свойствами на основе `releaseVersions`. При большом количестве различий допустима дополнительная секция Platform Support.
- Anatomy в первой версии — статическая визуальная схема с выносками. Стабильные идентификаторы частей могут в будущем позволить связать выноски с реальными слоями.
- Usage может содержать визуальные Do / Don't и текстовые рекомендации. Текстовые рекомендации берутся из раздела README «Рекомендации по использованию» (`documentation-manifest.md`, раздел 4.1). Рекомендации, не следующие напрямую из контракта, требуют утверждения перед фиксацией в README.

## 8. Генерация и синхронизация

```text
UI Contracts + правила документации + fixtures
                     ↓
          Figma Generation Skill
                     ↓
      Documentation Manifest (Git)
                     ↓
       Validator → Figma Plugin
                     ↓
       Generated Documentation
```

Манифест хранит стабильные логические идентификаторы секций и примеров. Целевая модель — **инкрементальное обновление** по этим идентификаторам. На первом этапе допускается полная пересборка Generated Documentation, но не Custom Documentation и не Component Set.

Синхронизация не обязана сохранять ручные правки внутри Generated Documentation; смешивать ручные и генерируемые изменения автоматически не планируется.

## 9. Проверка и согласование

- Skill предлагает состав секций, композиции, примеры и рекомендации; решения утверждаются перед сохранением.
- Независимый от Figma валидатор в будущем проверяет формат манифеста, ссылки, свойства, fixtures и существование композиционных шаблонов. Плагин дополнительно проверяет данные при загрузке.
- Спецификация Documentation Manifest версионируется отдельно от спецификации UI-контрактов. Текущие версии всех спецификаций указаны в `spec-versions.json` в корне репозитория (`schema-format.md`, раздел 11.3).

## 10. Не определено на этом этапе

- Формат композиционных шаблонов (`layouts/`, `sections/`) Documentation UI Library.
- Конкретный алгоритм обновления и хранения идентификаторов в Figma.
- Правила генерации интерактивных прототипов.
- Локализация документации (в первой версии тексты встроены в манифест, контракты и README).
