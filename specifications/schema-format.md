# Спецификация формата UI-контрактов

**Статус:** Черновик  
**Версия спецификации:** 0.9

## 1. Назначение

Эта спецификация определяет формат JSON-контрактов для описания независимых от платформы UI-типов, компонентов, их
свойств и взаимосвязей.

Контракты служат единым источником истины для реализаций на Android, iOS, Figma и других платформах.

Формат контрактов не зависит от конкретного языка программирования, UI-фреймворка или инструмента проектирования.

## 2. Основные принципы

1. Каждый контракт описывается отдельным JSON-документом.
2. Контракты определяют структуру и смысл UI-сущностей, а не детали их реализации.
3. Контракты могут ссылаться друг на друга для повторного использования определений.
4. Сложные типы могут собираться из более простых.
5. Вспомогательные определения могут использоваться для организации схем, не становясь самостоятельными публичными
   типами.
6. Доступность сущностей на разных платформах указывается явно.
7. Особенности реализации конкретной платформы не должны определять структуру общей модели.
8. Контракт описывает тип сущности, а не конкретные величины её значений (см. раздел 9).

## 3. Структура контракта

Контракт может содержать следующие поля:

| Поле              | Назначение                                                       |
|-------------------|------------------------------------------------------------------|
| `name`            | Имя сущности, определяемой контрактом.                           |
| `type`            | Тип описываемой сущности.                                        |
| `description`     | Текстовое описание сущности.                                     |
| `properties`      | Определяет свойства сущности (для `object`).                     |
| `values`          | Определяет значения перечисления (для `enum`).                   |
| `oneOf`           | Определяет альтернативные варианты (для `oneOf`).                |
| `releaseVersions` | Описывает доступность и версии реализации на целевых платформах. |

Применимость полей в зависимости от `type`:

| `type`   | `properties` | `values` | `oneOf` |
|----------|--------------|----------|---------|
| `object` | да           | нет      | нет     |
| `enum`   | нет          | да       | нет     |
| `oneOf`  | нет          | нет      | да      |

Полный набор полей и ограничения их использования будут уточняться по мере развития спецификации.

## 4. Типы

### 4.1. Примитивные типы

| Тип       | Назначение                                             |
|-----------|--------------------------------------------------------|
| `string`  | Строковое значение.                                    |
| `boolean` | Логическое значение `true` или `false`.                |
| `integer` | Целочисленное значение.                                |
| `float`   | Число с плавающей точкой одинарной точности (32 бита). |
| `color`   | Цвет в пространстве sRGB с прозрачностью.              |
| `payload` | Данные приложения, тип которых задаёт приложение.      |

Тип `double` не используется.

Для чисел с плавающей точкой применяется единый тип `float`, чтобы уменьшить различия между реализациями на разных
платформах.

Тип `payload` описывает данные, структуру которых задаёт приложение, а не контракт (например, данные события).
Контракт и дизайн-система такие данные не интерпретируют и передают без изменений.

| Платформа | Представление                                                                     |
|-----------|-----------------------------------------------------------------------------------|
| Android   | `interface Payload`; приложение реализует его своими моделями.                    |
| iOS       | `protocol Payload`; приложение реализует его своими типами, поле — `any Payload`. |

1. `Payload` — общий тип дизайн-системы без членов. Генераторы используют его для всех свойств типа `payload`.
2. Разбор `payload` из JSON выполняет приложение: регистрирует свои реализации `Payload` для полиморфной десериализации
   (например, `polymorphic(Payload::class)` в kotlinx.serialization). Дизайн-система формат данных не ограничивает.
3. Реализации `Payload` сравниваются по значению (`data class` и `data object` в Kotlin, `Hashable` в Swift), чтобы
   модели с одинаковыми данными были равны.

### 4.2. Составные типы

| Тип      | Назначение                                                   |
|----------|--------------------------------------------------------------|
| `object` | Объект, содержащий именованные свойства.                     |
| `enum`   | Перечисление именованных значений.                           |
| `oneOf`  | Сущность, принимающая ровно один из перечисленных вариантов. |
| `array`  | Упорядоченный набор элементов одного типа.                   |

Тип `array` используется только как тип свойства (раздел 5.1); самостоятельных контрактов этого типа нет.

Дополнительные составные типы будут вводиться по мере необходимости.

### 4.3. Независимость от платформ

Типы определяются на уровне общего контракта.

Например, `float` должен соответствовать 32-битному числу с плавающей точкой независимо от того, какая платформа
реализует контракт.

### 4.4. Перечисления

Значения перечисления задаются полем `values` — упорядоченным массивом объектов. Порядок значений значим.

Описание значения может содержать:

| Поле              | Назначение                                |
|-------------------|-------------------------------------------|
| `name`            | Имя значения.                             |
| `description`     | Назначение значения.                      |
| `releaseVersions` | Поддержка значения на целевых платформах. |

**Пример:**

```json
{
  "name": "SpacingScale",
  "type": "enum",
  "description": "Именованные значения шкалы отступов",
  "values": [
    { "name": "zero", "description": "Отсутствие отступа, 0 условных единиц" },
    { "name": "xs2", "description": "Минимальный отступ, по умолчанию 2 условные единицы" }
  ]
}
```

### 4.5. Запись значений

Конкретное значение типа (например, значение свойства в примере документации, в демонстрационных данных или в
значении по умолчанию) записывается в JSON по единым правилам:

| Тип                                           | Запись                                                                                 | Пример                         |
|-----------------------------------------------|----------------------------------------------------------------------------------------|--------------------------------|
| `string`                                      | Строка JSON.                                                                           | `"Продолжить"`                 |
| `boolean`                                     | `true` или `false`.                                                                    | `true`                         |
| `integer`                                     | Целое число JSON.                                                                      | `6`                            |
| `float`                                       | Число JSON.                                                                            | `1.5`                          |
| `color`                                       | Строка `#RRGGBB` или `#RRGGBBAA`: шестнадцатеричные цифры в верхнем регистре, sRGB.    | `"#C9A227"`, `"#1E2B4414"`     |
| `enum`                                        | Строка с именем значения.                                                              | `"xs2"`                        |
| `object`                                      | Объект: ключи — имена свойств, значения записаны по этим же правилам.                  | `{ "value": 6 }`               |
| `array`                                       | Массив JSON; элементы записаны по типу элементов.                                      | `[{ "click": { ... } }]`       |
| `payload`                                     | Любое значение JSON, кроме `null`; формат задаёт приложение.                            | `{ "action": "openProfile" }`  |
| `oneOf`, вариант из развёрнутого перечисления | Строка с именем варианта.                                                              | `"xs2"`                        |
| `oneOf`, остальные варианты                   | Объект с одним ключом — именем варианта; значение записано по типу контракта варианта. | `{ "custom": { "value": 6 } }` |

Правила:

1. Необязательное свойство без значения не указывается. `null` не используется.
2. Запись `object` содержит все обязательные свойства и не содержит ключей, не определённых контрактом.
3. Правила применяются рекурсивно. Если вариант `oneOf` ссылается на контракт типа `enum` или `oneOf`, значение внутри
   объекта записывается по правилам этого типа, например `{ "scale": "xs" }`.
4. Имена значений, вариантов и свойств — имена после разворачивания (раздел 7).
5. Необязательное свойство типа `array` без элементов не указывается: пустой массив не используется.
6. Для `color` последняя пара цифр в форме `#RRGGBBAA` задаёт прозрачность (`00` — полностью прозрачный, `FF` —
   непрозрачный). Форма `#RRGGBB` эквивалентна `#RRGGBBFF`. Генераторы самостоятельно приводят запись к формату
   платформы (например, `0xAARRGGBB` на Android).

## 5. Свойства

Свойства определяют структуру и характеристики сущности типа `object`.

Свойства задаются полем `properties` — упорядоченным массивом объектов. Порядок свойств значим: он может использоваться
генераторами, например, для порядка параметров конструктора.

Описание свойства может содержать:

| Поле              | Назначение                                     |
|-------------------|------------------------------------------------|
| `name`            | Имя свойства.                                  |
| `type`            | Тип значения свойства.                         |
| `$ref`            | Ссылка на контракт, задающий тип свойства.     |
| `description`     | Назначение свойства.                           |
| `required`        | Обязательность свойства.                       |
| `items`           | Тип элементов массива (для `"type": "array"`). |
| `uniqueVariants`  | Уникальность вариантов элементов массива.      |
| `releaseVersions` | Поддержка свойства на целевых платформах.      |

Тип свойства задаётся либо полем `type`, либо полем `$ref`.

Поле `required` указывает, обязательно ли передавать соответствующее свойство при создании или использовании сущности.

Дополнительные ограничения будут добавляться по мере необходимости.

### 5.1. Массивы

Свойство типа `array` задаёт тип элементов полем `items`. Поле `items` содержит либо `type` с примитивным типом, либо
`$ref` на контракт.

1. Вложенные массивы не используются: `items` не может иметь тип `array`.
2. `"uniqueVariants": true` допустимо, только если элементы — контракт типа `oneOf`. Каждый вариант встречается в
   массиве не более одного раза; порядок элементов не значим. Генераторы могут представлять такой массив множеством
   (например, `Set` в Kotlin).
3. Без `uniqueVariants` порядок элементов значим, повторы допустимы.

**Пример:**

```json
{
  "name": "events",
  "type": "array",
  "items": { "$ref": "../events/Event" },
  "uniqueVariants": true,
  "required": false,
  "description": "События компонента"
}
```

**Пример свойства объекта:**

```json
{
   "name": "SpacingCustom",
   "type": "object",
   "description": "Произвольный отступ вне шкалы",
   "properties": [
      {
         "name": "value",
         "type": "integer",
         "required": true,
         "description": "Величина отступа в условных единицах"
      }
   ]
}
```

## 6. Ссылки на другие контракты

Поле `$ref` позволяет ссылаться на другой контракт или переиспользуемое определение.

Это позволяет использовать существующие типы вместо повторного описания их структуры.

Правила записи ссылки:

1. Путь указывается относительно файла, содержащего ссылку.
2. Ведущий `/` не используется.
3. Расширение `.json` не указывается.

**Примеры:**

```json
{ "$ref": "SpacingScale" }
{ "$ref": "../spacing/Spacing" }
```

Правила обработки циклических зависимостей пока не утверждены.

## 7. Композиция типов

Сущность типа `oneOf` описывает набор альтернативных вариантов. Варианты задаются полем `oneOf` — упорядоченным
массивом элементов.

Элемент `oneOf` может содержать:

| Поле              | Назначение                                                                    |
|-------------------|-------------------------------------------------------------------------------|
| `$ref`            | Ссылка на контракт, описывающий вариант.                                      |
| `inline`          | Разворачивание значений перечисления в варианты родителя.                     |
| `name`            | Имя варианта в родительской сущности.                                         |
| `releaseVersions` | Поддержка варианта на целевых платформах.                                     |

Правила формирования вариантов:

1. Если элемент содержит `"inline": true`, он должен ссылаться на контракт типа `enum`. Каждое значение перечисления
   становится отдельным вариантом родительской сущности без промежуточной вложенности.
2. Если `inline` отсутствует или равен `false`, элемент образует один вариант. Имя варианта берётся из поля `name`, а
   при его отсутствии — из имени контракта, на который указывает `$ref`.
3. Поле `name` не используется вместе с `"inline": true`.
4. Если элемент ссылается на контракт типа `object`, данные варианта — свойства этого объекта. Если элемент ссылается на
   контракт другого типа (`enum`, `oneOf`), данные варианта — одно значение этого типа; генераторы представляют его
   полем с именем `value`. Например, вариант `fixed`, ссылающийся на `Size`, в Kotlin становится
   `data class Fixed(val value: Size)`.

**Пример:**

```json
{
  "name": "Spacing",
  "type": "oneOf",
  "oneOf": [
    { "$ref": "SpacingScale", "inline": true },
    { "$ref": "SpacingCustom", "name": "custom" }
  ]
}
```

**Ожидаемый результат на Kotlin:**

```kotlin
sealed interface Spacing {
    data object Zero : Spacing
    data object Xs2 : Spacing
    data class Custom(val value: Int) : Spacing
}
```

Контракты, на которые ссылаются элементы `oneOf`, являются вспомогательными определениями и не становятся
самостоятельными публичными типами, если иное не определено структурой каталогов (см. раздел 11).

## 8. Поддержка платформ

Поле `releaseVersions` определяет доступность контракта, свойства или значения на целевых платформах.

### 8.1. Поддерживаемые платформы

- `android`
- `ios`
- `figma`

### 8.2. Статусы

| Статус              | Значение                                          |
|---------------------|---------------------------------------------------|
| `released`          | Реализовано и доступно на указанной платформе.    |
| `notReleased`       | Пока не реализовано на указанной платформе.       |
| `willNotBeReleased` | Реализация на указанной платформе не планируется. |

### 8.3. Версии реализации

Для Android и iOS допускается указание конкретной версии, начиная с которой сущность доступна.

Версия относится к реализации дизайн-системы на соответствующей платформе, а не к версии операционной системы.

Для Figma достаточно статуса без указания версии.

Формат:

```json
{
  "releaseVersions": {
    "android": {
      "status": "released",
      "version": "1.0"
    },
    "ios": "notReleased",
    "figma": "released"
  }
}
```

Для Android и iOS допускается как сокращённая запись статуса строкой, так и объект с дополнительной информацией о
версии.

Для Figma используется только строковый статус.

### 8.4. Уровни применения

`releaseVersions` может указываться:

- На уровне контракта.
- На уровне отдельного свойства.
- На уровне значения перечисления.
- На уровне элемента `oneOf`.

### 8.5. Наследование статусов

1. **Наследование.** Если `releaseVersions` не указан у вложенного уровня целиком или для отдельной платформы, статус
   для этой платформы наследуется от родителя.
2. **Ограничение доступности.** Вложенный уровень не может быть доступнее родителя:

   | Статус родителя     | Допустимые статусы вложенного уровня        |
   |---------------------|---------------------------------------------|
   | `released`          | любой                                       |
   | `notReleased`       | `notReleased`, `willNotBeReleased`          |
   | `willNotBeReleased` | `willNotBeReleased`                         |

3. **Версии.** Версия вложенного уровня не может быть меньше версии родителя.
4. **Родитель при разворачивании.** Для значений перечисления, развёрнутого через `"inline": true`, и для элементов
   `oneOf` родителем считается контракт, содержащий `oneOf`.

Вспомогательные определения, на которые ссылаются элементы `oneOf`, не указывают собственный `releaseVersions` на уровне
контракта.

## 9. Значения

Контракт описывает тип сущности: набор вариантов, значений и свойств. Конкретные величины (например, размер отступа
`xs2`) хранятся отдельно от контрактов в файлах значений, сгруппированных в темы (раздел 9.4). Это позволяет задавать
разные величины для тем, брендов и режимов без изменения контракта.

Размерные величины задаются в условных единицах, которые платформа интерпретирует самостоятельно: `dp` на Android,
`pt` на iOS, `px` в Figma. Размеры текста (размер шрифта, межстрочный интервал, межбуквенный интервал) задаются в
условных единицах текста, которые масштабируются вместе с системной настройкой размера шрифта: `sp` на Android, `pt` на
iOS, `px` в Figma.

Величины, указанные в `description`, являются справочными. Источником истины для величин являются файлы значений.

### 9.1. Файл значений

Файл значений называется `<Имя>.values.json`, где `<Имя>` — имя контракта. Файлы значений публичных контрактов
располагаются в каталоге темы (раздел 9.4), например `themes/default/Spacing.values.json`. Файл значений внутреннего
контракта (раздел 11.1, правило 7) располагается рядом с этим контрактом.

Файл значений содержит следующие поля:

| Поле        | Назначение                                                                                                |
|-------------|-----------------------------------------------------------------------------------------------------------|
| `$ref`      | Ссылка на контракт, для которого задаются значения.                                                       |
| `valueType` | Тип величин: имя примитивного типа (раздел 4.1) или ссылка `{ "$ref": "..." }` на контракт типа `object`. |
| `modes`     | Упорядоченный массив режимов (например, тем) со значениями.                                               |

Описание режима содержит:

| Поле     | Назначение                                                                                  |
|----------|---------------------------------------------------------------------------------------------|
| `name`   | Имя режима.                                                                                 |
| `values` | Объект, ключи которого — имена вариантов, а значения — их величины или алиасы (раздел 9.3). |

**Пример:**

```json
{
  "$ref": "../../schemas/foundation/spacing/Spacing",
  "valueType": "integer",
  "modes": [
    {
      "name": "default",
      "values": {
        "zero": 0,
        "xs2": 2
      }
    }
  ]
}
```

### 9.2. Правила

1. `$ref` указывает на публичный или внутренний контракт сущности, а не на вспомогательное определение. Ключи
   `values` — имена вариантов контракта после разворачивания (раздел 7).
2. В каждом режиме значения задаются ровно для вариантов без свойств: для каждого такого варианта и только для них.
   Варианты со свойствами (например, `custom`) значениями не являются и в файл не включаются.
3. Все величины, включая итоговые величины алиасов, соответствуют типу `valueType`. Величины объектного типа
   записываются по разделу 4.5, например
   `{ "fontFamily": "Inter", "fontWeight": 400, "fontSize": 14, "lineHeight": 20 }`.
4. Первый режим в `modes` является режимом по умолчанию. Имена режимов записываются в `lowerCamelCase` и уникальны в
   пределах файла.
5. Все режимы содержат одинаковый набор ключей.
6. Порядок ключей внутри `values` не значим: порядок вариантов задаётся контрактом.

### 9.3. Алиасы

Величина в файле значений может быть ссылкой на величину варианта другого контракта:

```json
"onSurface": { "$ref": "ColorPalette", "value": "warmGray10" }
```

| Поле    | Назначение                                                                 |
|---------|----------------------------------------------------------------------------|
| `$ref`  | Ссылка на контракт, величина варианта которого используется (раздел 6).    |
| `value` | Имя варианта этого контракта.                                              |

1. Величина алиаса берётся из файла значений целевого контракта в той же теме. Для внутреннего контракта темы — из
   файла значений рядом с ним.
2. Если в целевом файле есть режим с тем же именем, используется он; иначе — первый режим целевого файла.
3. `valueType` целевого файла совпадает с `valueType` файла, содержащего алиас.
4. Алиас может ссылаться на другой алиас. Циклические ссылки запрещены.
5. Генераторы платформ подставляют итоговые величины; сохранение алиасов определяется платформой (например, в Figma
   алиасы становятся ссылками между переменными).

### 9.4. Темы

Тема — набор файлов значений для публичных контрактов. Темы располагаются в каталоге `themes/`; каждая тема — в
собственном каталоге с именем в `lowerCamelCase`.

```
themes/
  default/
    ColorPalette.json
    ColorPalette.values.json
    BorderWidth.values.json
    ColorRole.values.json
    CornerRadius.values.json
    Elevation.values.json
    FontFace.json
    FontFace.values.json
    FontFaceValue.json
    Size.values.json
    Spacing.values.json
    TypographyRole.values.json
    fonts/
```

1. Каталог темы плоский: в нём находятся файлы значений публичных контрактов и внутренние контракты темы (например,
   палитра) вместе с их файлами значений.
2. Тема `default` является темой по умолчанию и содержит файлы значений для всех публичных контрактов, у которых есть
   величины.
3. Другие темы могут задавать файлы значений только для части контрактов; для остальных используется тема `default`.
   Файл значений темы полностью заменяет соответствующий файл темы `default`.
4. Внутренние контракты темы не публикуются на платформах (раздел 11.1, правило 7); на них ссылаются алиасы файлов
   значений той же темы.
5. Файл значений темы, отличной от `default`, содержит как минимум все режимы соответствующего файла темы `default` и
   может добавлять собственные (например, режимы для письменностей, используемых продуктом).
6. Тема может содержать ресурсы, на которые ссылаются её файлы значений (например, файлы шрифтов в `fonts/`). Пути к
   ресурсам указываются относительно каталога темы.

## 10. Именование

| Сущность                              | Формат           | Пример                         |
|---------------------------------------|------------------|--------------------------------|
| Контракт (`name`, имя файла)          | `PascalCase`     | `Spacing`, `SpacingScale`      |
| Свойство, значение enum, вариант      | `lowerCamelCase` | `value`, `paddingHorizontal`   |
| Каталог сущности                      | `lowerCamelCase` | `spacing`, `iconSize`          |

Повторяемые размерные модификаторы записываются числовым суффиксом: `xs2` вместо `xxs`, `xl3` вместо `xxxl`.

Генераторы самостоятельно приводят имена к соглашениям целевой платформы. Например, `xs2` становится `Xs2` в Kotlin и
`spacing/xs2` в Figma.

## 11. Организация файлов

### 11.1. Структура каталогов

```
schemas/
  foundation/          — базовые сущности: отступы, скругления, цвета и т. д.
    spacing/
      README.md
      Spacing.json
      SpacingScale.json
      SpacingCustom.json
  core/                — основа модели компонентов: базовая модель, раскладка
    component/
      README.md
      Component.json
    layout/
      README.md
      Layout.json
      ...
  components/          — компоненты
themes/                — темы: файлы значений (раздел 9.4)
  default/
    Spacing.values.json
```

1. Каждая публичная сущность располагается в собственном каталоге внутри каталога слоя.
2. Публичным контрактом каталога является файл, имя которого совпадает с именем каталога в `PascalCase`. Например,
   `spacing/Spacing.json`.
3. Остальные файлы `<Имя>.json` в каталоге являются вспомогательными определениями этой сущности.
4. Величины публичных сущностей хранятся не в каталоге сущности, а в темах (раздел 9.4).
5. Файлы с составным расширением `<Имя>.<вид>.json` не являются контрактами; их формат определяют соответствующие
   спецификации:

   | Файл                | Назначение                   | Спецификация                |
   |---------------------|------------------------------|-----------------------------|
   | `<Имя>.values.json` | Величины сущности.           | Раздел 9.1.                 |
   | `<Имя>.figma.json`  | Проект Figma-компонента.     | `figma-mapping.md`          |
   | `<Имя>.docs.json`   | Манифест документации Figma. | `documentation-manifest.md` |

6. Слои каталога `schemas/`:

   | Слой          | Назначение                                                                                              |
   |---------------|---------------------------------------------------------------------------------------------------------|
   | `foundation/` | Базовые сущности дизайн-системы с величинами в темах: отступы, цвета, типографика и т. д.               |
   | `core/`       | Основа модели компонентов: базовая модель `Component`, раскладка (`specifications/component-model.md`). |
   | `components/` | Компоненты.                                                                                             |

   Дополнительные слои вводятся по мере необходимости.
7. Контракты вне каталога `schemas/` являются внутренними: они не публикуются на платформах и не указывают
   `releaseVersions`. Остальные правила спецификации к ним применяются. Примеры: палитра темы (раздел 9.4), токены
   библиотеки оформления документации в `figma/documentation/tokens/` (`figma-documentation.md`, раздел 5).

### 11.2. README сущности

Каждый каталог сущности содержит `README.md` с информацией, которая не выражается в JSON:

1. **Назначение** — что это за сущность и когда её применять.
2. **Состав** — файлы каталога и их роль.
3. **Варианты** — перечень вариантов и справочные величины по умолчанию.
4. **Рекомендации по использованию** — типичные сценарии применения вариантов.
5. **Ограничения и открытые вопросы.**

Разделы записываются заголовками второго уровня (`##`) с названиями точно в указанном виде. Раздел «Рекомендации по
использованию» является источником текста для документации Figma (`documentation-manifest.md`, раздел 4.1).

README не дублирует машиночитаемые данные контракта, такие как статусы платформ. Источником истины является контракт.

### 11.3. Версии спецификаций

В корне репозитория располагается файл `spec-versions.json` с текущими версиями спецификаций:

```json
{
  "schemaFormat": "0.9",
  "figmaMapping": "0.6",
  "documentationManifest": "0.3"
}
```

1. Версии в `spec-versions.json` совпадают с версиями в заголовках соответствующих спецификаций.
2. Все файлы репозитория (контракты, файлы значений, `<Имя>.figma.json`, `<Имя>.docs.json`) соответствуют этим
   версиям. Отдельные файлы версию формата не указывают.
3. Изменение спецификации, требующее правки существующих файлов, выполняется в одном коммите с переносом этих файлов и
   обновлением `spec-versions.json`.
4. Инструменты (валидатор, плагин, генераторы) проверяют `spec-versions.json` и отказываются обрабатывать
   неподдерживаемые версии.

## 12. Валидация

В будущем контракты должны проверяться на соответствие актуальной версии спецификации.

Предполагаются следующие проверки:

1. Корректность JSON и наличие обязательных полей.
2. Поддерживаемость типов и допустимость комбинаций полей.
3. Корректность ссылок на другие контракты.
4. Совместимость типов.
5. Согласованность статусов поддержки платформ, включая правила наследования (раздел 8.5).
6. Корректность формата версий реализации.
7. Соответствие используемых конструкций текущей версии спецификации.
8. Соответствие правилам именования и организации файлов.
9. Полнота и корректность файлов значений и тем (разделы 9.2, 9.4), корректность алиасов (раздел 9.3).
10. Соответствие записей значений типам (раздел 4.5), включая уникальность вариантов в массивах (раздел 5.1).
11. Соответствие `spec-versions.json` версиям спецификаций (раздел 11.3).

Способ реализации валидатора пока не определён.

## 13. Открытые вопросы

Следующие аспекты требуют дальнейшего обсуждения:

1. **Обязательные поля:** какие поля обязательны для каждого вида контракта и свойства.
2. **Числовые типы:** допустимый диапазон `integer` и правила обработки переполнения.
3. **Ссылки:** обработка циклических зависимостей.
4. **Ограничения:** допустимые значения, диапазоны, значения по умолчанию и другие ограничения свойств (например,
   неотрицательность `SpacingCustom.value`).
5. **Темы:** выбор темы и режима приложением (например, режима типографики по языку), наследование тем помимо
   `default`, представление продуктовых тем в Figma.
10. **Типографика на iOS:** сопоставление ролей типографики с системными стилями текста iOS для масштабирования
    собственных шрифтов (Dynamic Type).
6. **Публичность:** достаточно ли соглашения по имени файла или требуется явный признак вспомогательного определения.
7. **Версионирование контрактов:** изменения контрактов и обратная совместимость.
8. **Версионирование спецификации:** правила совместимости версий для инструментов, обрабатывающих контракты (общий
   порядок перехода определён в разделе 11.3).
9. **Валидация:** механизм проверки контрактов и совместимости используемых конструкций.
