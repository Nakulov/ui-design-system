# Формат набора данных плагина

**Статус:** Черновик для согласования  
**Версия спецификации:** 0.12

## 1. Назначение

Набор данных (`bundle.json`) — один файл, в котором плагин Figma получает всё, что ему нужно из репозитория:
контракты, величины темы, отображение в Figma, примеры моделей, демо-экраны, рисунки символов, тексты README, элементы оформления,
манифесты документации и журналы изменений. Плагин работает в песочнице Figma и не видит файлы репозитория, поэтому данные доставляются набором.

Набор — производный файл. Его собирает `tools/bundle.py` из проверенного репозитория; в Git он не хранится.

Набор — нормализованный граф: ссылки в нём уже разрешены инструментом, и плагин не повторяет правила разрешения
ссылок (`schema-format.md`, раздел 6) и поиска файлов значений (раздел 9).

## 2. Идентификаторы

1. Идентификатор контракта — логический `<слой>/<сущность>/<Имя>` без корня `contracts/` и без `definitions/`,
   например `components/badge/Badge` и `components/badge/BadgeContent`; у внутреннего контракта темы — путь от
   корня репозитория без `.json`, например `themes/default/ColorPalette` (`schema-format.md`, раздел 6). Он
   совпадает с ключом `ref` в `sharedPluginData` объектов Figma (`figma-mapping.md`, раздел 7.1).
2. Вариант, пример или символ указывается после `#`: `themes/default/ColorPalette#gold68`,
   `components/badge/Badge#count`, `foundation/icon/Icon#close`.

## 3. Структура

```json
{
  "specVersions": { "schemaFormat": "0.18", "figmaMapping": "0.16", "documentationManifest": "0.3", "bundleFormat": "0.2" },
  "source": { "commit": "48bcb86f…", "committedAt": "2026-10-26T11:40:00+03:00", "branch": "dev", "dirty": false },
  "theme": "default",
  "contracts": {
    "components/badge/Badge": { "name": "Badge", "extends": "core/component/Component", "…": "…" }
  },
  "values": {
    "foundation/colorRole/ColorRole": {
      "valueType": "color",
      "modes": [
        { "name": "light", "values": { "primary": { "alias": "themes/default/ColorPalette#gold68" } } }
      ]
    }
  },
  "figma": { "foundation/spacing/Spacing": { "scopes": ["GAP"] } },
  "samples": { "components/badge/Badge#count": { "Badge": { "…": "…" } } },
  "screens": { "androidMessages": { "Container": { "…": "…" } } },
  "icons": { "foundation/icon/Icon#close": { "svg": "<svg …>", "mirrored": false } },
  "texts": { "components/badge/Badge": { "Назначение": "…", "Рекомендации по использованию": "…" } },
  "documentation": { "figma/documentation/elements/heading": { "holes": { "…": "…" }, "model": { "Text": { "…": "…" } } } },
  "manifests": { "core/layout/Layout": { "sections": [ { "id": "overview", "type": "overview" } ] } },
  "changelogs": { "components/badge/Badge": { "entries": [ { "date": "2026-10-23", "kind": "added", "…": "…" } ] } },
  "checklist": { "items": [ { "number": 1, "kind": "auto", "text": "…", "appliesTo": ["component", "foundation", "core"] } ] }
}
```

| Поле            | Содержимое                                                                       |
|-----------------|----------------------------------------------------------------------------------|
| `specVersions`  | Содержимое `spec-versions.json`, по которому собран набор.                       |
| `source`        | Состояние репозитория, из которого собран набор (раздел 3.11).                   |
| `theme`         | Имя темы. Пока всегда `default`.                                                 |
| `contracts`     | Все контракты репозитория по идентификаторам (раздел 3.1).                       |
| `values`        | Файлы значений темы по идентификатору контракта, к которому они относятся (3.2). |
| `figma`         | Файлы `figma.json` по идентификатору контракта (раздел 3.6).                     |
| `samples`       | Примеры моделей из каталогов `samples/` (раздел 3.3).                            |
| `screens`       | Демо-экраны из каталога `screens/` (раздел 3.9).                                 |
| `icons`         | Рисунки символов (раздел 3.4).                                                   |
| `texts`         | Разделы README сущностей (раздел 3.5).                                           |
| `documentation` | Элементы оформления документации, превью величин и демонстрации (раздел 3.7).    |
| `manifests`     | Манифесты документации (раздел 3.8).                                             |
| `changelogs`    | Журналы изменений сущностей (раздел 3.10).                                       |
| `checklist`     | Пункты чеклиста готовности к релизу в Figma (раздел 3.12).                       |

### 3.1. Контракты

1. Контракт переносится целиком, со всеми полями, включая `description` и `releaseVersions`.
2. Значения `$ref` и `extends` заменяются идентификаторами целевых контрактов (раздел 2).
3. Все ссылки указывают на контракты, присутствующие в `contracts`.

### 3.2. Значения

1. Ключ — идентификатор контракта, на который ссылается `$ref` файла значений, например
   `foundation/spacing/Spacing` или `themes/default/ColorPalette` для внутреннего контракта темы.
2. `valueType` — примитив строкой или `{ "$ref": "<идентификатор>" }`.
3. `modes` — массив режимов в порядке файла значений; первый режим — режим по умолчанию.
4. Алиас (`schema-format.md`, раздел 9.3) не разворачивается в величину и записывается как
   `{ "alias": "<идентификатор контракта>#<вариант>" }`. Режим цели выбирается по правилу 2 раздела 9.3: режим с тем
   же именем, иначе первый.
5. Пути ресурсов (`source`) записываются от корня репозитория, например `themes/default/icons/close.svg`.

### 3.3. Примеры

1. Ключ — `<идентификатор публичного контракта сущности>#<имя файла примера без .json>`.
2. Значение — модель из файла примера без изменений, включая сгенерированные `min` и `max`.

### 3.4. Символы

1. Ключ — `<идентификатор контракта Icon>#<вариант>`.
2. `svg` — содержимое файла рисунка, `mirrored` — признак из файла значений.

### 3.5. Тексты

1. Ключ — идентификатор публичного контракта сущности, README которой прочитан. Описание системы `docs/overview.md`
   (`figma-documentation.md`, раздел 3) хранится под ключом `docs/overview`.
2. Значение — объект: ключи — заголовки разделов второго уровня (`schema-format.md`, раздел 11.2) в порядке README,
   значения — текст раздела в исходном Markdown без заголовка.

### 3.6. Отображение в Figma

1. Ключ — идентификатор контракта, на который ссылается `$ref` файла `figma.json` (`figma-mapping.md`,
   раздел 6).
2. Значение — содержимое файла без `$ref`. Ссылки внутри, если появятся, переписываются по разделу 3.1.

### 3.7. Элементы оформления документации

1. Ключ — путь файла без `.json`: превью величин и демонстрации лежат в сущности, и путь берётся от `contracts/`,
   например `foundation/spacing/preview` и `core/layout/demos/widthSizing`; элемент оформления — от корня
   репозитория, например `figma/documentation/elements/heading`.
2. Значение — содержимое файла как есть: `holes` и `model` (`figma-documentation.md`, раздел 5).

### 3.8. Манифесты документации

1. Ключ — идентификатор контракта, на который ссылается `$ref` манифеста `docs.json`
   (`documentation-manifest.md`, раздел 3).
2. Значение — содержимое манифеста без `$ref`; `demo` примеров заменено идентификатором демонстрации в
   `documentation` (раздел 3.7), например `core/layout/demos/widthSizing`, а `sample` — ключом примера в
   `samples` (раздел 3.3), например `components/text/Text#label` для `label` в манифесте `Text` и для
   `Text#label` в манифесте другого компонента.
3. Каждая демонстрация манифеста есть в `documentation`, каждый пример — в `samples`.

### 3.9. Демо-экраны

Демо-экраны — модели целых экранов из нескольких компонентов для проверки импорта и обновления макетов на месте.
Они не документируют компонент, поэтому лежат не в `samples/`, а в каталоге `screens/` в корне репозитория: один
файл — один экран.

1. Ключ — имя файла без `.json` в lowerCamelCase, например `androidMessages`.
2. Значение — модель экрана без изменений в формате примеров (`schema-format.md`, раздел 11.1, правило 8): объект с
   одним ключом — именем публичного компонента слоя `components`, обычно `Container`.
3. `tools/validate.py` проверяет экраны по контрактам так же, как примеры, и требует канонический формат файла.

### 3.10. Журналы изменений

1. Ключ — идентификатор публичного контракта, на который ссылается `$ref` журнала `changelog.json`
   (`schema-format.md`, раздел 11.4), например `components/badge/Badge`.
2. Значение — содержимое журнала без `$ref`: записи `entries` целиком, от новых к старым.
3. Плагин берёт из журнала переименования (`kind: "renamed"`), чтобы сохранять узлы Figma при обновлении
   (`figma-mapping.md`, раздел 7).

### 3.11. Источник

Поле `source` обязательно и описывает состояние репозитория, из которого собран набор. Его берёт из Git
`tools/bundle.py`, поэтому набор одного коммита воспроизводим: повторная сборка даёт тот же файл.

| Поле          | Содержимое                                                                                  |
|---------------|---------------------------------------------------------------------------------------------|
| `commit`      | Полный хеш `HEAD`.                                                                          |
| `committedAt` | Время коммита `HEAD` в ISO 8601 со смещением (`git show -s --format=%cI`), а не время сборки. |
| `branch`      | Текущая ветка; при отсоединённом `HEAD` — значение `--branch` (раздел 5), иначе `null`.     |
| `dirty`       | `true`, если `git status --porcelain` не пуст: набор собран с незакоммиченными изменениями. |

Вне Git-репозитория `commit`, `committedAt` и `branch` — `null`, `dirty` — `false`.

Плагин показывает источник в сводке: ветку, короткий хеш и время коммита, а при `dirty: true` — пометку
«есть незакоммиченные изменения».

### 3.12. Чеклист готовности

Содержимое `figma/releaseChecklist.json` как есть: `items` — пункты чеклиста готовности к релизу в Figma
(`figma-mapping.md`, раздел 8.5). Плагин рисует их во фрейме Release Checklist (`figma-documentation.md`,
раздел 3.5) и не держит их текст у себя.

## 4. Совместимость

1. Плагин поддерживает одну версию формата `bundleFormat`: совпадает основная версия, а до версии 1.0 — и
   дополнительная (до 1.0 каждая версия может быть несовместима с предыдущей).
2. Набор неподдерживаемой версии плагин не открывает и сообщает, какая версия ему нужна. Для набора, загруженного
   с GitHub (раздел 6), сообщение предлагает обновить плагин: набор там всегда собран из актуального `dev`.
3. Версии других спецификаций в `specVersions` плагин показывает в сводке; правила их проверки появятся вместе с
   использованием соответствующих данных.

## 5. Сборка

1. `tools/bundle.py` сначала выполняет проверки `tools/validate.py`. При ошибках набор не собирается.
2. Набор записывается в `build/bundle.json` (параметр `--out` задаёт другой файл). Каталог `build/` в Git не
   хранится.
3. Перед записью инструмент проверяет, что все ссылки набора (раздел 3.1, правило 3; алиасы и `valueType`; демонстрации и
   примеры манифестов, раздел 3.8) указывают на существующие сущности.
4. Параметр `--branch <имя>` задаёт `source.branch`, если `HEAD` отсоединён (так собирает CI). При обычной
   работе с веткой он не нужен: ветка определяется сама.

## 6. Доставка

1. **GitHub Pages — основной путь.** При каждом push в `dev` CI (job `publish` в `.github/workflows/validate.yml`)
   после успешных проверок собирает набор (`bundle.py --branch dev`) и публикует его на GitHub Pages:
   `https://nakulov.github.io/ui-design-system/bundle.json`. На Pages лежит один набор — из последнего коммита
   `dev`, без истории.
2. Плагин загружает набор кнопкой «Загрузить с GitHub» (`fetch` с `cache: "no-store"`) и разбирает его так же, как
   файл. Адрес набора редактируемый: продукт может подключить свой набор. Изменённый адрес хранится в
   `figma.clientStorage`; пустое поле — адрес по умолчанию.
3. Pages кэширует файл до 10 минут: сразу после merge плагин может получить предыдущий набор. Какой именно,
   видно по `source` в сводке.
4. **Файл.** Набор, собранный локально, открывается кнопкой «Открыть файл…». Этот путь нужен, чтобы проверить
   ветку задачи до merge в `dev`.

## 7. Не определено на этом этапе

- Наборы тем, отличных от `default` (этап 4 `ROADMAP.md`).
