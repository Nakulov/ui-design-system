# Формат Documentation Manifest

**Статус:** Черновик для согласования  
**Версия спецификации:** 0.3

## 1. Назначение

Documentation Manifest — декларативный, версионируемый документ, описывающий **содержание** документации одной публичной сущности — компонента или foundation-сущности — в Figma. Он не содержит Figma node IDs и не определяет конкретные Frame/Text/Instance слои.

Контракт остаётся источником истины для свойств и доступности платформ; манифест ссылается на контракт, не копируя его определения.

## 2. Предлагаемая структура

```json
{
  "$ref": "Button",
  "sections": [
    {
      "id": "overview",
      "type": "overview",
      "title": "Button",
      "examples": [
        {
          "id": "mainPreview",
          "props": {
            "style": "primary",
            "size": "medium",
            "text": "Продолжить"
          }
        }
      ]
    },
    {
      "id": "variants",
      "type": "variants",
      "layout": "comparisonGrid",
      "title": "Варианты",
      "examples": [
        {
          "id": "primaryMedium",
          "props": {
            "style": "primary",
            "size": "medium",
            "text": "Продолжить"
          }
        },
        {
          "id": "secondaryMedium",
          "props": {
            "style": "secondary",
            "size": "medium"
          },
          "fixture": "shortActionText"
        }
      ]
    },
    {
      "id": "usage",
      "type": "usage",
      "title": "Использование",
      "examples": [
        {
          "id": "singlePrimary",
          "verdict": "do",
          "caption": "Одна основная кнопка в группе действий",
          "props": {
            "style": "primary",
            "size": "medium",
            "text": "Продолжить"
          }
        }
      ]
    }
  ]
}
```

**Важно:** `Button`, его свойства и значения в примере вымышлены; это иллюстрация формата, а не ссылка на уже существующий контракт. Имена `comparisonGrid` и `shortActionText` также демонстрационные — библиотеки пока нет.

**Пример для foundation-сущности:**

```json
{
  "$ref": "Spacing",
  "sections": [
    { "id": "overview", "type": "overview", "title": "Spacing" },
    { "id": "scale", "type": "values", "title": "Шкала", "layout": "sizeBars" },
    { "id": "usage", "type": "usage", "title": "Использование" }
  ]
}
```

Описание берётся из `Spacing.json`, переменные `spacing/*` и их величины — из `themes/default/Spacing.values.json`, рекомендации — из README (раздел 4.1). Вариант `custom` в шкалу не попадает: в файле значений его нет. Имя композиции `sizeBars` демонстрационное.

## 3. Поля верхнего уровня

| Поле | Тип | Назначение |
|---|---|---|
| `$ref` | string | Ссылка на публичный контракт документируемой сущности. |
| `sections` | array | Упорядоченные декларативные секции документации. |

Версию формата манифест не указывает: все файлы репозитория соответствуют версиям спецификаций из `spec-versions.json` (`schema-format.md`, раздел 11.3).

Файл манифеста располагается в каталоге сущности рядом с её публичным контрактом и называется `<Имя>.docs.json`, например `button/Button.docs.json`. Файл манифеста не является контрактом (`schema-format.md`, раздел 11.1).

`$ref` записывается по правилам `schema-format.md`, раздел 6: путь относительно файла манифеста, без ведущего `/` и расширения `.json`. Ссылка указывает на публичный контракт сущности, а не на вспомогательное определение. Поскольку манифест лежит рядом с контрактом, `$ref` содержит только имя контракта.

В первой версии собственные тексты манифеста (заголовки секций, подписи примеров) записываются непосредственно в манифест; обязательной системы локализации нет. Описания и рекомендации манифест не хранит (раздел 4.1).

## 4. Секции

Каждая секция имеет:

- `id` — стабильный логический идентификатор в пределах манифеста, используемый при синхронизации;
- `type` — тип секции из утверждённой библиотеки;
- `layout` — необязательный идентификатор разрешённой композиции, совместимой с типом секции;
- поля содержимого, соответствующие конкретному `type` (например, `title`, `examples`).

Порядок секций в `sections` определяет порядок в документации. Перечень типов секций и допустимых полей для каждого типа будет формализован после проверки на реальных компонентах.

### 4.1. Источники текстов

Манифест не повторяет тексты, у которых уже есть источник в репозитории:

| Содержание | Источник | Где выводится |
|---|---|---|
| Краткое описание сущности | `description` публичного контракта | Overview |
| Рекомендации по использованию | Раздел README «Рекомендации по использованию» (`schema-format.md`, раздел 11.2) | Usage |
| Величины вариантов | Файл значений `<Имя>.values.json` темы `default` (`schema-format.md`, раздел 9.4) | Values |

1. Плагин читает эти тексты при построении документации; манифест не содержит их копий.
2. Раздел README находится по заголовку, зафиксированному в `schema-format.md`, раздел 11.2. Отсутствующий или пустой раздел не выводится.
3. В манифесте остаются только тексты, относящиеся к самой документации: заголовки секций и подписи примеров (`caption`).
4. Рекомендации утверждаются при изменении README, а не манифеста.

### 4.2. Секции по видам сущностей

| Секции | Компоненты | Foundation-сущности |
|---|---|---|
| Overview, Usage | да | да |
| Values | — | да |
| Anatomy, Properties, Variants, States, Edge Cases, Layout Behavior | да | — |

1. **Values** строится целиком из публичного контракта и файла значений; примеров в манифесте не содержит. Для каждого варианта из файла значений выводятся имя переменной Figma (`figma-mapping.md`, раздел 3.1), величины по режимам и описание из контракта. Вид образца (например, полосы для размеров или плашки для цветов) задаётся `layout`.
2. **Overview** содержит основной пример только у компонентов; у foundation-сущностей пример отсутствует.
3. **Usage** у foundation-сущностей содержит только текст из README.

### 4.3. Именование

Имена в манифесте следуют `schema-format.md`, раздел 10:

1. `id` секций и примеров, идентификаторы композиций (`layout`) и имена fixtures записываются в `lowerCamelCase`, например `mainPreview`, `comparisonGrid`, `shortActionText`.
2. Значения `type` — имена типов секций в `lowerCamelCase`: `overview`, `anatomy`, `properties`, `variants`, `states`, `edgeCases`, `layoutBehavior`, `usage`, `platformSupport`, `values`.
3. Имена контрактов в `$ref` указываются без префиксов. Префикс, если он нужен платформе, добавляет её генератор.

## 5. Демонстрационные примеры

Примеры применимы только к сущностям, отображаемым в Figma-компонент — Component или Component Set (`figma-mapping.md`, раздел 3.2). Каждый пример имеет:

| Поле | Назначение |
|---|---|
| `id` | Стабильный идентификатор внутри секции. |
| `$ref` | Необязательная ссылка на публичный контракт, по которому создаётся instance. По умолчанию — контракт манифеста. |
| `props` | Явно заданные значения свойств контракта: объект, ключи — имена свойств, значения записаны по `schema-format.md`, раздел 4.5. |
| `fixture` | Необязательная ссылка на именованный набор демонстрационных данных. |
| `caption` | Необязательная подпись к примеру. |
| `verdict` | Только для секции Usage: `do` или `dont` — пример рекомендуемого или нежелательного использования. |

`props` и `fixture` можно комбинировать. **Предлагаемое правило:** сначала применяются значения fixture, затем `props` переопределяет совпадающие ключи. Это правило требует отдельного утверждения.

Указывать `$ref` в примере нужно, только если пример показывает другой компонент, например в Usage или при сравнении с похожим компонентом. Путь записывается так же, как `$ref` верхнего уровня.

Вместо Figma IDs используются ссылки на контракты и имена их свойств. Сопоставление контрактов и их свойств с Figma-компонентами определяет `figma-mapping.md`.

### 5.1. Допустимые свойства и значения

Пример создаётся как instance реального Figma-компонента, поэтому в нём допустимо только то, что существует в Figma:

1. Правило применяется к `props` примеров и к значениям fixtures. Секции, описывающие контракт текстом (например, Properties), перечисляют все свойства контракта, включая недоступные в Figma.
2. Каждое свойство и каждое значение в примере должны иметь итоговый статус `figma`, отличный от `willNotBeReleased`. Статусы `released` и `notReleased` допустимы: документацию можно готовить до публикации компонента.
3. Итоговый статус определяется с учётом наследования (`schema-format.md`, раздел 8.5): контракт → свойство → значение перечисления или элемент `oneOf`.
4. Значение свойства должно быть представимо как значение свойства Figma-компонента (`figma-mapping.md`, раздел 4). Варианты со свойствами (например, `custom`) в примерах не используются.
5. Обязательные свойства контракта, недоступные в Figma, в примере не указываются.
6. Значения записываются одинаково независимо от вида свойства в Figma. Значение свойства, отображённого в режим (`figma-mapping.md`, раздел 3.3), плагин применяет к instance как выбор режима соответствующей коллекции.

## 6. Fixtures

Fixtures содержат повторно используемые демонстрационные данные, например `shortActionText`, `emptyText`, `longText`. Они не являются частью публичного UI-контракта. Значения в fixtures записываются по `schema-format.md`, раздел 4.5.

Точное расположение, формат и область видимости fixtures пока не утверждены. Валидатор должен уметь обнаруживать отсутствующие и некорректные ссылки на них.

## 7. Связь с контрактом

При проверке манифеста необходимо удостовериться, что:

1. Контракты, указанные в `$ref` манифеста и примеров, существуют и являются публичными.
2. Каждый используемый `props` определён контрактом, получает допустимое значение и доступен в Figma по разделу 5.1.
3. Имена вариантов и свойства соответствуют правилам UI-контракта, включая развёрнутые `oneOf` и `$ref`.
4. Данные `releaseVersions` читаются из контракта, а не дублируются в манифесте.
5. Указанные типы секций и композиции поддерживаются Documentation UI Library.

При этом проверка реального наличия нужного Figma-компонента выполняется отдельно при построении страницы.

## 8. Стабильные идентификаторы и обновление

`id` секций и примеров — логические идентификаторы, которые не должны изменяться при правках текста, порядка или оформления. Их назначение — поддерживать сопоставление элементов между генерациями.

В первой версии плагин может пересобирать Generated Documentation полностью. В дальнейшем он сможет обновлять только изменившиеся элементы. Манифест не хранит Figma node IDs.

## 9. Валидация

Планируемый независимый валидатор проверяет:

- структуру манифеста и обязательные поля;
- уникальность `id` в соответствующей области;
- корректность ссылок на контракты и свойств;
- существование fixtures и совместимость их значений;
- существование и допустимость композиционных шаблонов.

Реализация валидатора откладывается до появления нескольких реальных манифестов.

## 10. Открытые вопросы

1. Нужны ли отдельные типизированные структуры для каждого `type` секции или универсальные блоки содержимого?
2. Где и в каком формате хранить fixtures; допустимы ли вложенные/составные данные?
3. Правила приоритета при одновременном использовании `fixture` и `props`.
4. Как представлять темы и режимы, параметры контейнера, визуальные выноски Anatomy и интерактивные сценарии?
5. Нужна ли уникальность `id` во всём манифесте или достаточно внутри родительской секции?
6. Как версионировать совместимость манифестов с библиотекой композиций?
7. Какое подмножество Markdown из README поддерживается при выводе в Figma?
8. Как показывать визуальные Do / Don't для foundation-сущностей, у которых нет instances?

Эти вопросы намеренно не закрыты выдуманными правилами: их нужно проверить при проектировании первых реальных примеров.
