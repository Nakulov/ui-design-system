# Формат Documentation Manifest

**Статус:** Черновик для согласования  
**Версия спецификации:** 0.11

## 1. Назначение

Documentation Manifest — декларативный, версионируемый документ, описывающий **содержание** документации одной публичной сущности — компонента или foundation-сущности — в Figma. Он не содержит Figma node IDs и не определяет конкретные Frame/Text/Instance слои.

Контракт остаётся источником истины для свойств и доступности платформ; манифест ссылается на контракт, не копируя его определения.

## 2. Структура

```json
{
  "$ref": "Badge",
  "sections": [
    { "id": "overview", "type": "overview", "examples": [ { "id": "main", "sample": "count", "caption": "Счётчик" } ] },
    { "id": "properties", "type": "properties", "title": "Properties" },
    {
      "id": "variants",
      "type": "variants",
      "title": "Variants",
      "examples": [
        { "id": "dot", "sample": "dot", "caption": "Точка без содержимого" },
        { "id": "count", "sample": "count", "caption": "Счётчик" }
      ]
    },
    { "id": "usage", "type": "usage", "title": "Usage" },
    { "id": "platformSupport", "type": "platformSupport", "title": "Platform Support" },
    { "id": "history", "type": "history", "title": "History" }
  ]
}
```

Манифест есть у компонентов и сущностей core. У foundation-сущностей манифеста нет: их страница строится по правилу
(`figma-documentation.md`, раздел 3.1).

1. Манифест обязателен у каждого публичного компонента и каждой публичной сущности core, доступных в Figma: итоговый
   статус `figma` контракта — не `willNotBeReleased`. Сущность, которой в Figma нет (`Event`), манифеста и страницы не
   имеет. Это проверяет валидатор.
2. Манифест вне компонентов и core валидатор отклоняет.

## 3. Поля верхнего уровня

| Поле | Тип | Назначение |
|---|---|---|
| `$ref` | string | Ссылка на публичный контракт документируемой сущности. |
| `sections` | array | Упорядоченные декларативные секции документации. |

Версию формата манифест не указывает: все файлы репозитория соответствуют версиям спецификаций из `spec-versions.json` (`schema-format.md`, раздел 11.3).

Файл манифеста располагается в каталоге сущности рядом с её публичным контрактом и называется `docs.json`, например `button/docs.json`. Файл манифеста не является контрактом (`schema-format.md`, раздел 11.1).

`$ref` записывается по правилам `schema-format.md`, раздел 6: имя контракта своей сущности. Ссылка указывает на главный контракт сущности, а не на вспомогательное определение.

В первой версии собственные тексты манифеста (заголовки секций, подписи примеров) записываются непосредственно в манифест; обязательной системы локализации нет. Описания и рекомендации манифест не хранит (раздел 4.1).

## 4. Секции

Каждая секция имеет:

- `id` — стабильный логический идентификатор в пределах манифеста, используемый при синхронизации;
- `type` — тип секции из утверждённой библиотеки;
- `layout` — необязательный идентификатор разрешённой композиции, совместимой с типом секции;
- поля содержимого, соответствующие конкретному `type` (например, `title`, `examples`).

Порядок секций в `sections` определяет порядок в документации. Допустимые типы и поля секций — раздел 4.2.

### 4.1. Источники текстов

Манифест не повторяет тексты, у которых уже есть источник в репозитории:

| Содержание | Источник | Где выводится |
|---|---|---|
| Краткое описание сущности | `description` публичного контракта | Overview |
| Рекомендации по использованию | Раздел README «Рекомендации по использованию» (`schema-format.md`, раздел 11.2) | Usage |
| Величины вариантов | Файл значений `<Имя>.values.json` темы `default` (`schema-format.md`, раздел 9.4) | Values |
| Выпуски по платформам | `releaseVersions` всех уровней контрактов каталога (`schema-format.md`, разделы 8, 11.4) | Platform Support |
| Изменения API | Журнал `changelog.json` сущности (`schema-format.md`, раздел 11.4) | History |

1. Плагин читает эти тексты при построении документации; манифест не содержит их копий.
2. Раздел README находится по заголовку, зафиксированному в `schema-format.md`, раздел 11.2. Отсутствующий или пустой раздел не выводится.
3. В манифесте остаются только тексты, относящиеся к самой документации: заголовки секций и подписи примеров (`caption`).
4. Рекомендации утверждаются при изменении README, а не манифеста.
5. Раздел «Рекомендации по использованию» записан подмножеством Markdown (`schema-format.md`, раздел 11.2). Плагин
   переводит его в модели компонентов и рисует их ядром отрисовки (`figma-mapping.md`, раздел 10), поэтому документация
   показывает систему её же средствами, в том числе в тёмной теме:

   | Markdown                              | Модель                                                                                                      |
   |---------------------------------------|-------------------------------------------------------------------------------------------------------------|
   | абзац                                 | `Text`                                                                                                      |
   | маркированный или нумерованный список | `Container` (`vertical`) строк: `Container` (`horizontal`) из `Text` с маркером («•», «1.») и `Text` пункта |
   | `код в строке`, **жирный**, ссылка    | фрагменты `Text` (`rich`) со своей ролью типографики, цветом и линией                                       |

   Например, пункт README `Badge` «- Цвет текста и символа берите парным к фону: `onError` на `error`» становится строкой
   списка, где `onError` и `error` — фрагменты с моноширинной ролью. Роли, цвета и отступы документации задаёт
   библиотека оформления (`figma-documentation.md`, раздел 5); моноширинной роли типографики в системе пока нет.

### 4.2. Секции по видам сущностей

| Секции | Компоненты | Core | Foundation-сущности |
|---|---|---|---|
| Overview, Usage, History | да | да | да, без манифеста |
| Values | — | — | да, без манифеста |
| Properties, Variants, Platform Support | да | да | — |
| States, Layout Behavior | позже | да | — |
| Anatomy, Edge Cases | позже | — | — |

1. **Values** строится целиком из файла значений: для каждого варианта — имя, величины по режимам и превью из шаблона `preview.json` сущности (`figma-documentation.md`, разделы 3.1 и 5).
2. **Overview** содержит основной пример только у компонентов; у core и foundation-сущностей пример отсутствует.
3. **Usage** у foundation-сущностей содержит только текст из README.
4. **Поля секций.** У каждой секции, кроме `overview`, есть `title`. `properties`, `usage`, `platformSupport` и
   `history` не содержат примеров: их содержание берётся из контракта, README и журнала изменений (раздел 4.1). Других полей, кроме перечисленных ниже, секции не имеют.
5. **Секции core:** `overview` без примеров; `variants`, `states` и `layoutBehavior` с непустым списком `examples` из
   демонстраций (раздел 5.2).
6. **Секции компонентов:** `overview` ровно с одним примером — основным; `variants` с непустым списком `examples`;
   `properties`, `usage`, `platformSupport` и `history`. Примеры компонентов — образцы из `samples/` (раздел 5.1).
   Anatomy, States и сравнение тем у компонентов появятся позже.
7. **Properties** у core: у объекта — строки полей, у `oneOf` — строки вариантов; имя, тип, описание и платформы,
   выпущенные по итоговому статусу `releaseVersions` (`figma-documentation.md`, раздел 3.3).
8. **Properties** у компонента: строки его собственных свойств, как у core, и последней строкой `Component` — базовая
   модель списком полей `Component`, у `appearance` — с контекстами из `appearanceContext` компонента:
   «Базовая модель: id, layout, padding, appearance (plain, control), indicators, events». Поля базовой модели
   отдельными строками не выводятся: они одинаковы у всех компонентов и описаны на странице `Component`.
9. **History** — все записи журнала `changelog.json` сущности от новых к старым: дата, вид, цель и описание
   (`figma-documentation.md`, раздел 3.1). У компонентов и core секция обязательна, одна и последняя: страницы
   следуют общему шаблону. У foundation-сущностей она стоит последней по правилу.
10. **Platform Support** — выпуски сущности по платформам из итоговых статусов `releaseVersions` контрактов каталога:
    по каждой платформе — статус и версия контракта, ниже — уровни, с которых начинается более поздняя версия
    (`figma-documentation.md`, раздел 3.3). У компонентов и core секция обязательна, одна и стоит непосредственно перед
    `history`. У foundation-сущностей её нет: сводка по десяткам токенов почти ничего не даёт.

### 4.3. Именование

Имена в манифесте следуют `schema-format.md`, раздел 10:

1. `id` секций и примеров и идентификаторы композиций (`layout`) записываются в `lowerCamelCase`, например `main`, `comparisonGrid`.
2. Значения `type` — имена типов секций в `lowerCamelCase`: `overview`, `anatomy`, `properties`, `variants`, `states`, `edgeCases`, `layoutBehavior`, `usage`, `platformSupport`, `values`, `history`.
3. Имена контрактов в `$ref` указываются без префиксов. Префикс, если он нужен платформе, добавляет её генератор.

## 5. Примеры

Пример секции — модель, нарисованная ядром отрисовки (`figma-mapping.md`, раздел 10). У компонента пример — образец из
его `samples/` (раздел 5.1), у сущности core — демонстрация (раздел 5.2): у core нет ни Figma-компонента, ни своих
образцов. Смешивать нельзя: `sample` у core и `demo` у компонента валидатор отклоняет.

### 5.1. Примеры компонентов

```json
{ "id": "count", "sample": "count", "caption": "Счётчик" }
```

| Поле | Назначение |
|---|---|
| `id` | Стабильный идентификатор внутри секции. |
| `sample` | Имя файла образца без `.json` из каталога `samples/` компонента; образец другого компонента — `<Контракт>#<имя>`, например `Text#label`. |
| `caption` | Необязательная подпись. |

1. Образец уже проверена валидатором (`schema-format.md`, раздел 11.1) и рисуется так же, как на странице
   `Samples`: компоненты — экземплярами Figma-компонентов библиотеки, `Container` — фреймом (`figma-mapping.md`,
   разделы 3.4 и 10). Свойства и значения в манифесте не повторяются.
2. Ссылка `sample` указывает на существующий образец публичного компонента. Сгенерированные `min` и `max` проверяют
   ветки ядра отрисовки, а не вид, и в документации не используются. Это проверяет валидатор.
3. Подпись — текст документации, поэтому она в манифесте, а не в файле образца (раздел 4.1).
4. Ядро отрисовки рисует экземпляр в состоянии `default` (`figma-mapping.md`, раздел 10.1, правило 2), поэтому
   примеры показывают вид по умолчанию; состояния компонентов — секция States, позже.

### 5.2. Демонстрации

Демонстрация — готовая модель компонента, которая показывает поведение сущности core: `hug` против `fill`, закрепление,
вид состояний, индикаторы. Её рисует ядро отрисовки (`figma-mapping.md`, раздел 10), а не инстанс Figma-компонента.

```json
{ "id": "widthSizing", "demo": "widthSizing", "caption": "hug, fill и fixed по ширине одного родителя" }
```

| Поле | Назначение |
|---|---|
| `id` | Стабильный идентификатор внутри секции. |
| `demo` | Имя файла демонстрации без `.json` из каталога `demos/` сущности. |
| `caption` | Необязательная подпись. |

1. Файл демонстрации лежит в каталоге сущности, `demos/<имя>.json` (`schema-format.md`, раздел 11.1), и записан форматом элемента
   оформления без дырок (`figma-documentation.md`, раздел 5): модель нужна только документации и не входит в образцы
   компонента.
2. Подпись — текст документации, поэтому она в манифесте, а не в файле демонстрации (раздел 4.1).
3. Каждая демонстрация используется хотя бы одним манифестом; ссылка `demo` указывает на существующий файл. Это
   проверяет валидатор.
4. Ядро отрисовки рисует только показанное состояние оформления (`figma-mapping.md`, раздел 10.1, правило 2). Вид
   других состояний демонстрация показывает срезом: моделью с `plain`, равным оформлению этого состояния.

## 6. Связь с контрактом

При проверке манифеста необходимо удостовериться, что:

1. Контракт, указанный в `$ref` манифеста, существует, является публичным и лежит рядом с манифестом.
2. Примеры `sample` ссылаются на существующие образцы публичных компонентов, `demo` — на существующие демонстрации.
3. Данные `releaseVersions` читаются из контракта, а не дублируются в манифесте.

Наличие нужного Figma-компонента проверяется отдельно при построении страницы.

## 7. Стабильные идентификаторы и обновление

`id` секций и примеров — логические идентификаторы, которые не должны изменяться при правках текста, порядка или оформления. Их назначение — поддерживать сопоставление элементов между генерациями.

В первой версии плагин может пересобирать Generated Documentation полностью. В дальнейшем он сможет обновлять только изменившиеся элементы. Манифест не хранит Figma node IDs.

## 8. Валидация

`tools/validate.py` проверяет:

- наличие манифеста у каждой сущности по разделу 2 и отсутствие манифестов у остальных;
- канонический формат файла, поля верхнего уровня и `$ref` на контракт рядом с манифестом;
- типы секций и их поля по разделу 4.2, `title`, `id` в `lowerCamelCase` и их уникальность;
- что секция `history` у компонентов и core есть, одна и последняя (раздел 4.2, правило 9);
- что секция `platformSupport` у компонентов и core есть, одна и стоит перед `history` (раздел 4.2, правило 10);
- примеры: `sample` только у компонентов и на существующий образец, кроме `min` и `max`; `demo` только у core и на
  существующий файл; ровно один пример в Overview компонента;
- что каждая демонстрация используется хотя бы одним манифестом.

## 9. Открытые вопросы

1. Нужны ли отдельные типизированные структуры для каждого `type` секции или универсальные блоки содержимого?
2. Как представлять темы и режимы, параметры контейнера, визуальные выноски Anatomy и интерактивные сценарии?
3. Нужна ли уникальность `id` во всём манифесте или достаточно внутри родительской секции?
4. Как версионировать совместимость манифестов с библиотекой композиций?
5. Как показывать визуальные Do / Don't в Usage?

Эти вопросы намеренно не закрыты выдуманными правилами: их нужно проверить при проектировании первых реальных примеров.
