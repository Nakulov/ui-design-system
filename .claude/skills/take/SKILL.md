# Задача в работу

## Ход работы

1. **Старт.** Прочитай задачу с комментариями (`gh issue view <N> --comments`), заметку «текущая работа» в памяти
   Claude и состояние ветки (`git status -sb`): если ветка `task/<N>-…` уже есть, продолжай в ней. Если в «Решении» или «Открытых вопросах» есть нерешённое, что влияет на
   работу, — обсуди с пользователем до начала изменений.
2. **Ветка.** От актуального `dev`: `git switch dev && git pull --ff-only && git switch -c task/<N>-<slug>`, где
   `<slug>` — 1–3 слова латиницей через дефис. Поставь задаче статус: `tools/board.sh status <N> in-progress`.
3. **Изменения.** Делай то, что записано в «Решении» и «Объёме изменений», по правилам `contract-authoring` и
   спецификаций. Изменения вне задачи не вноси — предложи отдельную задачу.
   **Журнал изменений:** если менялся API контрактов каталога (свойства, варианты, значения, типы, обязательность),
   добавь запись в начало `changelog.json` этого каталога: дата, `issue` — номер задачи, `kind`, `target` и
   описание для дизайнера (`schema-format.md`, раздел 11.4). Правки `description`, `sample`, `releaseVersions` и
   перенос формата записи не требуют.
4. **Решения по ходу.** Если в работе пришлось решить то, чего нет в задаче, или отступить от неё, — согласуй с
   пользователем и запиши комментарием в задачу: `gh issue comment <N> --body …`.
5. **Roadmap и памятка.** Если задача меняет статус слоя в разделе «Где мы сейчас» `ROADMAP.md` (что есть, чего нет, ссылки на
   задачи), обнови таблицу в том же PR.
   Если задача меняет скиллы, слова или команды процесса, обнови `WORKFLOW.md` в том же PR.
6. **Проверка.** Если менялись контракты или образцы, запусти `python3 tools/sync.py`: он генерирует
   `samples/min.json` и `samples/max.json`, обновляет блоки образцов в README и список контрактов в
   `.idea/jsonSchemas.xml`. Затем
   `python3 tools/validate.py --base origin/dev` без ошибок; пройди «Критерии готовности» задачи и
   отметь выполненные в теле задачи.
   Новые термины из изменения (понятия и новые значения слов) есть в глоссарии `specifications/glossary.md`.
7. **Проверка в Figma.** Если задача меняет плагин или то, что он рисует (контракты, образцы, тему), пересобери набор
   (`python3 tools/bundle.py`) и плагин (`npm run build` в `figma-plugin/`) и дай пользователю сценарий проверки: что
   открыть, что нажать, что должно получиться. Figma Desktop и плагин запускает пользователь: через MCP плагин не
   запускается. Проверяют оба, по очереди:
   1. **Claude через Figma MCP** (скилл `figma:figma-use`), после того как пользователь отрисовал, — сначала
      структура, потом картинки. Найденное на любом шаге исправь и попроси перерисовать до проверки пользователя.
      1. **Структура** — одним вызовом `use_figma` на все затронутые образцы: дерево по меткам `uiContracts`,
         порядок, размеры, роли и `id`, дубли, тексты, привязки переменных. Выводи компактно — только эти поля, без
         полного дерева свойств. Пока структура не сошлась, скриншоты не снимай.
      2. **Скриншоты** — только то, что данными не проверить (обрезка, перекрытия, отступы на глаз, цвет темы).
         Снимай карточку или узел, а не страницу; не переснимай то, что не менялось с прошлого прогона.
   2. **Пользователь** — глазами в Figma; его подтверждение — переход к коммиту.

   Правила MCP:
   - по умолчанию только чтение;
   - эксперименты — во временном фрейме `… (temp)` на странице Samples; удаляй его в том же сеансе;
   - правка отрисованных образцов — только для проверки поведения и с предупреждением; после неё пользователь
     перерисовывает;
   - тестовый файл — в памяти Claude; если ссылки нет, спроси;
   - если MCP недоступен (не авторизован), проверяет только пользователь.

   Приёмы MCP:
   - слои ищи по меткам плагина в `sharedPluginData` (`uiContracts`: `ref`, `slot`, `role`), а не по типу или имени:
     первый `TEXT` в карточке — её подпись, а не текст образца;
   - скриншот намного дороже чтения структуры: снимай только по пункту 7.1.2;
   - один вызов `use_figma` возвращает одну картинку: на каждый скриншот — отдельный вызов;
   - не создавай узлы вне временного фрейма: `createInstance()` и `createRectangle()` кладут узел на текущую страницу;
   - сверяй вид на экране пользователя с данными слоёв: Figma Desktop может показывать не то, что лежит в слое
     (например, заглушку вместо значения переменной), а MCP при чтении это скрывает.

   Отладка: если Figma показывает не то, что ожидалось, сначала воспроизведи расхождение на временной копии узла во
   фрейме `… (temp)` и найди причину; правь код или данные только после этого, а не по догадке с перерисовкой.

   Образцы и расхождения:
   - Временные проверки делай только временными именованными образцами (`samples/<случай>.json`). `min.json` и
     `max.json` вручную не правь: `bundle.py` запускает `validate.py`, а он сверяет их с генерацией. Если образец
     встроен в README, синхронизируй README временно (`sync.py`) и откати его вместе с образцом до коммита.
   - Расхождения с живым Figma записывай в `figma-mapping` в том же PR.
8. **Коммиты.** Покажи пользователю итог и получи согласие на коммит. Сообщение — на английском, в стиле истории
   репозитория (заголовок, пустая строка, пункты).
9. **PR.** `git push -u origin HEAD`, затем `gh pr create --base dev` по шаблону `.github/pull_request_template.md`:
   `Closes #<N>`, изменения, отклонения от задачи, проверки. Поставь задаче статус
   `tools/board.sh status <N> in-review` и дай ссылку на PR. PR — точка сброса: предложи пользователю `/clear`.
10. **Замечания к PR** исправляй новыми коммитами в ту же ветку. Сливает пользователь (squash); после слияния
   переключись на `dev` и обнови его.

## Экономия контекста

- **Чтение.** Спецификации, контракты и код не читай целиком: найди заголовок или строку (`grep -n`) и прочитай нужный
  диапазон.
- **Передача.** По слову пользователя «закругляемся» запиши всё незаписанное: решения — комментарием в задачу,
  план — в заметку «текущая работа» в памяти Claude (что сделано, где остановились, следующий шаг). Ответь одной
  строкой, где что лежит.
- **Точки сброса** — после груминга и после PR; посреди работы контекст не сбрасывай: договорённости, не записанные в
  задачу или память, теряются.

## Границы

- В `dev` напрямую не коммить и не пушь: ветка защищена, изменения только через PR.
- Не сливай PR и не закрывай задачу сам.
