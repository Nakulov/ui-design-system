# Задача в работу

## Ход работы

1. **Старт.** Сначала свежая папка: если папка не на ветке открытой задачи (detached HEAD или ветка слитой задачи),
   выполни `git fetch origin && git switch --detach origin/dev`; ветку открытой задачи не трогай. Если обновление
   изменило этот скилл (`.claude/skills/take/SKILL.md`), перечитай его и дальше следуй новому тексту.
   Затем прочитай задачу с комментариями (`gh issue view <N> --comments`), заметку своей линии работы в памяти
   Claude (линия — по папке сессии, `WORKFLOW.md`, «Параллельная работа») и состояние ветки (`git status -sb`):
   если ветка `task/<N>-…` уже есть и её PR не слит, продолжай в ней. Проверь, есть ли у задачи long-term ветка
   (`git branch -r --list 'origin/feature/<N>-*'`): если есть, задача идёт через неё (`WORKFLOW.md`, «Размер PR») —
   после слияния маленького PR задача открыта, и следующий PR начинается с шага 3 от свежей long-term ветки, а не от
   `origin/dev`. Тело задачи — действующее решение, комментарии — история:
   при расхождении действует тело. Если в «Решении» или «Открытых вопросах» есть нерешённое, что влияет на работу, — обсуди с пользователем до начала изменений. Если задача —
   подзадача эпика, сверь её строку в таблице «Подзадачи» эпика («Что даёт», «Зависит от») с объёмом задачи;
   расхождение обсуди с пользователем.
2. **План PR до кода.** Оцени число изменённых файлов по «Объёму изменений» задачи и коду. В лимит не входят тестовые
   ресурсы (JSON в `src/test/resources`) и файлы, порождённые `tools/sync.py` (`samples/min.json`, `samples/max.json`,
   блоки образцов в README, `.idea/jsonSchemas.xml`). Покажи план пользователю и получи согласие до первого изменения:
   - **до 10 файлов** — план одного PR в `dev` в 3–5 строк: проблема, файлы и зачем каждый, примерный объём;
   - **больше 10** — таблица маленьких PR в long-term ветку: «PR | Проблема | Файлов» и строка «Итог → `dev`», как в
     примере #266. Каждый PR решает свою проблему, а не «часть задачи».

   Если по ходу работы план меняется, сначала покажи новый план или таблицу. Задача на ≤ 10 файлов выросла больше 10 —
   покажи таблицу и переведи задачу на long-term ветку: сделанное становится первым маленьким PR.
3. **Ветка.** Не переключаясь на `dev` (он может быть открыт в другой папке worktree), где `<slug>` — 1–3 слова
   латиницей через дефис:
   - задача до 10 файлов — от свежего `origin/dev`: `git fetch origin && git switch -c task/<N>-<slug> origin/dev`;
   - задача больше 10 — long-term ветка создаётся один раз от `origin/dev`:
     `git fetch origin && git push origin origin/dev:refs/heads/feature/<N>-<slug>-longterm`; ветка каждого маленького
     PR — от свежей long-term ветки: `git fetch origin && git switch -c task/<N>-<slug> origin/feature/<N>-<slug>-longterm`
     (`<slug>` маленького PR — по его проблеме).

   Поставь задаче статус: `tools/board.sh status <N> in-progress`.
4. **Изменения.** Делай то, что записано в «Решении» и «Объёме изменений», по правилам `contract-authoring` и
   спецификаций. Изменения вне задачи не вноси — предложи отдельную задачу.
   **Журнал изменений:** если менялся API контрактов каталога (свойства, варианты, значения, типы, обязательность),
   добавь запись в начало `changelog.json` этого каталога: дата, `issue` — номер задачи, `kind`, `target` и
   описание для дизайнера (`schema-format.md`, раздел 11.4). Правки `description`, `sample`, `releaseVersions` и
   перенос формата записи не требуют.
5. **Решения по ходу.** Если в работе пришлось решить то, чего нет в задаче, или отступить от неё, — согласуй с
   пользователем и запиши в тело задачи (`gh issue edit <N> --body-file …`): в «Решение» (или «Объём изменений»,
   «Критерии готовности») и в «Результаты обсуждения». Затем оставь комментарий — уведомление и история: что и почему
   поменялось (`gh issue comment <N> --body …`).
6. **Roadmap и памятка.** Если задача меняет статус слоя в разделе «Где мы сейчас» `ROADMAP.md` (что есть, чего нет, ссылки на
   задачи), обнови таблицу в том же PR.
   Если задача меняет скиллы, слова или команды процесса, обнови `WORKFLOW.md` в том же PR.
7. **Проверка.** Если менялись контракты или образцы, запусти `python3 tools/sync.py`: он генерирует
   `samples/min.json` и `samples/max.json`, обновляет блоки образцов в README и список контрактов в
   `.idea/jsonSchemas.xml`. Затем
   `python3 tools/validate.py --base origin/dev` без ошибок — и для PR в long-term ветку: версия спецификации
   поднимается один раз на задачу относительно `dev`. Если менялся `generator/`, в нём без ошибок
   `./gradlew check` (тесты, порог покрытия Kover и detekt) и `./gradlew run --args=../contracts` (все контракты разрешаются).
   Пройди «Критерии готовности» задачи и отметь выполненные в теле задачи.
   Новые термины из изменения (понятия и новые значения слов) есть в глоссарии `specifications/glossary.md`.
8. **Проверка в Figma.** Если задача меняет плагин или то, что он рисует (контракты, образцы, тему), пересобери набор
   (`python3 tools/bundle.py`) и плагин (`npm run build` в `figma-plugin/`) и дай пользователю сценарий проверки: что
   открыть, что нажать, что должно получиться. Figma Desktop и плагин запускает пользователь: через MCP плагин не
   запускается. Проверяют оба, по очереди:
   1. **Claude через Figma MCP** (скилл `figma:figma-use`), после того как пользователь отрисовал, — сначала
      структура, потом картинки. Найденное на любом шаге исправь и попроси перерисовать до проверки пользователя.
      1. **Структура** — одним вызовом `use_figma` на все затронутые образцы: дерево по меткам `uiContracts`,
         порядок, размеры, роли и `id`, дубли, тексты, привязки переменных. Выводи компактно — только эти поля, без
         полного дерева свойств. Пока структура не сошлась, скриншоты не снимай.
      2. **Скриншоты** — только то, что данными не проверить (обрезка, перекрытия, отступы на глаз, цвет темы).
         Снимай карточку или узел, а не страницу; не переснимай то, что не менялось с прошлого прогона.
   2. **Пользователь** — глазами в Figma; его подтверждение — переход к коммиту.

   Правила MCP:
   - по умолчанию только чтение;
   - эксперименты — во временном фрейме `… (temp)` на странице Samples; удаляй его в том же сеансе;
   - правка отрисованных образцов — только для проверки поведения и с предупреждением; после неё пользователь
     перерисовывает;
   - тестовый файл — в памяти Claude; если ссылки нет, спроси;
   - если MCP недоступен (не авторизован), проверяет только пользователь.

   Приёмы MCP:
   - слои ищи по меткам плагина в `sharedPluginData` (`uiContracts`: `ref`, `slot`, `role`), а не по типу или имени:
     первый `TEXT` в карточке — её подпись, а не текст образца;
   - скриншот намного дороже чтения структуры: снимай только по пункту 8.1.2;
   - один вызов `use_figma` возвращает одну картинку: на каждый скриншот — отдельный вызов;
   - не создавай узлы вне временного фрейма: `createInstance()` и `createRectangle()` кладут узел на текущую страницу;
   - сверяй вид на экране пользователя с данными слоёв: Figma Desktop может показывать не то, что лежит в слое
     (например, заглушку вместо значения переменной), а MCP при чтении это скрывает.

   Отладка: если Figma показывает не то, что ожидалось, сначала воспроизведи расхождение на временной копии узла во
   фрейме `… (temp)` и найди причину; правь код или данные только после этого, а не по догадке с перерисовкой.

   Образцы и расхождения:
   - Временные проверки делай только временными именованными образцами (`samples/<случай>.json`). `min.json` и
     `max.json` вручную не правь: `bundle.py` запускает `validate.py`, а он сверяет их с генерацией. Если образец
     встроен в README, синхронизируй README временно (`sync.py`) и откати его вместе с образцом до коммита.
   - Расхождения с живым Figma записывай в `figma-mapping` в том же PR.
9. **Коммиты.** Покажи пользователю итог и получи согласие на коммит. Сообщение — на английском, в стиле истории
   репозитория (заголовок, пустая строка, пункты).
10. **PR.** `git push -u origin HEAD`, затем `gh pr create` по шаблону `.github/pull_request_template.md`: проблема на
   примере, что меняет PR (было → стало), изменения — зачем каждое, на что обратить внимание, отклонения от задачи,
   проверки.
   - Задача до 10 файлов — `--base dev`, `Closes #<N>`; статус `tools/board.sh status <N> in-review`.
   - Маленький PR — `--base feature/<N>-<slug>-longterm`, `Part of #<N>` (`Closes` срабатывает только при слиянии в
     `dev`, задачу закрывает итоговый PR); статус остаётся In progress.
   - Итоговый PR, когда все маленькие PR слиты, — из ветки `task/<N>-final` от long-term ветки, в которую `dev`
     подлит слиянием, не rebase:
     `git fetch origin && git switch -c task/<N>-final origin/feature/<N>-<slug>-longterm && git merge origin/dev`,
     затем `gh pr create --base dev`, `Closes #<N>`, в «Изменениях» — список маленьких PR; статус
     `tools/board.sh status <N> in-review`. Его смотрит владелец сам. Почему не из самой long-term ветки: PR в неё
     сливаются squash, и коммиты `dev` в её историю не попадают, а `strict` у `dev` требует, чтобы последний коммит
     `dev` был в истории ветки PR; merge в `task/<N>-final` их туда кладёт.

   Дай полную ссылку на PR. PR — точка сброса: предложи пользователю `/clear`.
11. **Замечания к PR** исправляй новыми коммитами в ту же ветку. Сливает пользователь, все PR — одним коммитом
   (squash): маленькие в long-term ветку и итоговый в `dev`. После слияния выполни `git fetch origin`.
   - Маленький PR слит — задача открыта: следующий PR — с шага 3 от свежей long-term ветки. `dev` в long-term ветку
     раньше итогового PR подливай, только если в `dev` изменились файлы задачи: `git merge origin/dev` в ветке
     маленького PR от long-term ветки.
   - PR в `dev` слит — задача закрыта; следующая задача начнётся с шага 2 от свежего `origin/dev`. Ветка слитого PR
     остаётся открытой до следующей задачи; освободить папку — `git switch --detach origin/dev`.
   Если задача — подзадача эпика:
   - проверь, что в таблице «Подзадачи» эпика нет устаревшего (название, «Что даёт», зависимости) и она совпадает со
     списком подзадач (`gh api repos/{owner}/{repo}/issues/<эпик>/sub_issues`); устаревшее исправь в теле эпика;
   - если это последняя открытая подзадача эпика компонента — проверь критерий готовности эпика: задачи на пресеты
     закрыты, сделаны или отклонены с причиной. Эпик закрывает пользователь.

## Экономия контекста

- **Чтение.** Спецификации, контракты и код не читай целиком: найди заголовок или строку (`grep -n`) и прочитай нужный
  диапазон.
- **Передача.** По слову пользователя «закругляемся» запиши всё незаписанное: решения — в тело задачи и
  комментарием (шаг 5), план — в заметку своей линии работы в памяти Claude (что сделано, где остановились, следующий
  шаг). Ответь одной строкой, где что лежит.
- **Точки сброса** — после груминга и после PR; посреди работы контекст не сбрасывай: договорённости, не записанные в
  задачу или память, теряются.

## Границы

- В `dev` и long-term ветки `feature/*` напрямую не коммить и не пушь: ветки защищены, изменения только через PR.
  Исключение — создание long-term ветки (шаг 3).
- Не сливай PR и не закрывай задачу сам.
- Не начинай изменения без согласованного плана PR (шаг 2).
