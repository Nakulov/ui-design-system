# Roadmap

Общие границы и направление развития дизайн-системы: к чему стремимся, что не делаем, где мы сейчас и в каком порядке
движемся. Номера `#N` — задачи в [GitHub Issues](https://github.com/Nakulov/ui-design-system/issues), этапы —
[вехи](https://github.com/Nakulov/ui-design-system/milestones).

## Видение

Дизайн-система описывается один раз — в контрактах. Контракты — платформонезависимые данные и единый источник истины
для четырёх потребителей:

| Потребитель | Когда использует контракты | Что получает                                                           |
|-------------|----------------------------|------------------------------------------------------------------------|
| Figma       | при проектировании         | библиотеку с документацией; отрисовку модели в макет                   |
| Темы        | при сборке библиотеки      | бренд переопределяет значения темы `default`, продукт расширяет шкалы  |
| Платформы   | при сборке приложения      | модели, разбор и ресурсы темы для Android и iOS; отрисовку компонентов |
| Сервер      | во время работы            | схемы и проверку моделей; экраны как деревья моделей (SDUI)            |

- **Figma.** Импорт создаёт библиотеку: переменные в светлом и тёмном режимах, символы, компоненты во всех вариантах.
  Страницы документации описывают систему, foundation и core с демонстрацией, а для каждого компонента по общему
  шаблону — свойства, состояние релиза, историю изменений, работу с компонентом в Figma и на платформах. Второй режим
  плагина отрисовывает модель в макет.
- **Темы.** Бренд меняет цвета, шрифты, радиусы, не трогая компоненты: тема наследует `default` и задаёт только
  отличия. Продукт расширяет шкалы своими именами: символами, ролями, размерами.
- **Платформы.** Генераторы строят из контрактов модели, разбор и ресурсы темы для Compose и SwiftUI. Отрисовка
  компонентов пишется руками в отдельном репозитории.
- **SDUI.** Экран — дерево моделей, собранное на сервере или в приложении. Клиент никогда не падает и не отрисовывает
  неизвестное.

Над примитивами лежат типовые компоненты (пресеты) с узким API. Новые сущности проектируются вместе с ассистентом по
скиллам из `.claude/skills/`.

## Границы

Не входит:

| Не делаем                                                          | Почему                                                                                          |
|--------------------------------------------------------------------|-------------------------------------------------------------------------------------------------|
| Логика в моделях: условия, вычисления, привязка к данным, сценарии | Модель — только данные. События — сигналы наружу, обрабатывает их приложение                    |
| Возможности, которые нельзя выразить в Figma                       | Макет и экран не должны расходиться                                                             |
| Запасные варианты (fallback) в контрактах                          | Клиент не отрисовывает неизвестное (#4)                                                         |
| Синхронизация Figma → контракты                                    | Figma — потребитель, а не источник: правка в Figma не попадает в контракты                      |
| Отрисовка компонентов в этом репозитории                           | Здесь контракты, темы, инструменты, генераторы и плагин Figma; реализация — в отдельном         |
| Навигация, загрузка данных, кэш, аналитика в SDUI                  | SDUI отрисовывает дерево моделей; всё вокруг экрана делает приложение                           |
| Платформы кроме Compose и SwiftUI: веб, View, UIKit                | Фокус; формат не мешает добавить их потом                                                       |
| Продуктовые компоненты («статус заказа», «карточка товара»)        | В системе только общие компоненты и пресеты; продуктовое собирается из них или живёт в продукте |
| Анимации и переходы — пока                                         | Плохо выражаются в Figma и сложны для SDUI                                                      |

Возможно позже: экспорт токенов в стандартные форматы (W3C Design Tokens, Style Dictionary) — ещё один потребитель тем.

Входит позже, а не исключено: доступность, продуктовые шкалы, пресеты.

## Этапы

Этапы 1–5 — вехи GitHub; задачи и эпики привязываются к вехам.

### Этап 0. Основа — готово

Формат контрактов, инструменты проверки и синхронизации, foundation, core, компоненты Container, Text, Image, Badge.

### Этап 1. Импорт в Figma (MVP)

- **Цель:** проверить гипотезу, что из контрактов получается рабочая библиотека с документацией.
- **Состав:**
  - данные для документации: формат (#20), история изменений, манифесты четырёх компонентов, тексты для дизайнера;
  - плагин: переменные со светлым и тёмным режимами, символы, страницы foundation и core с демонстрацией, компоненты
    во всех вариантах, страницы компонентов по шаблону;
  - живая проверка отображения (#5, #33).
- **Критерий завершения:** импорт темы `default` в пустой файл воспроизводим, дизайнер собирает макет из библиотеки
  без ручных правок.

На время MVP плагин живёт в этом репозитории; вынос в отдельный — открытый вопрос.

### Этап 2. Figma: обновление и отрисовка модели

- **Цель:** библиотека живёт вместе с контрактами, и SDUI видно уже в Figma.
- **Состав:**
  - повторный импорт обновляет библиотеку, а не создаёт её заново: экземпляры в макетах не ломаются;
  - история изменений на страницах компонентов;
  - режим «отрисовка модели»: JSON превращается в макет.
- **Критерий завершения:** изменение контракта после повторного импорта отражается в библиотеке и макетах; примеры
  моделей отрисовываются в Figma.

### Этап 3. Темы

- **Цель:** бренд без правки компонентов.
- **Состав:** наследование от `default`, переопределение значений, выбор темы при импорте.
- **Критерий завершения:** тестовая тема задаёт только отличия, импортируется в Figma и проходит проверку.

### Этап 4. Генераторы и платформы

- **Цель:** одни контракты дают код.
- **Состав:**
  - генерация моделей, разбора по правилам совместимости (#4, #40) и ресурсов темы;
  - JSON Schema моделей (#17);
  - отдельный репозиторий с отрисовкой четырёх компонентов на Compose и SwiftUI;
  - решение о Kotlin Multiplatform для сгенерированного слоя.
- **Критерий завершения:** примеры моделей одинаково отрисовываются на Android, iOS и в Figma.

### Этап 5. SDUI

- **Цель:** экраны с сервера.
- **Состав:** валидатор для приложений (#16), продуктовые шкалы (#22), версионирование на практике.
- **Критерий завершения:** экран с сервера отрисовывается на обеих платформах; неизвестное отбрасывается и логируется.

### Вне этапов

- **Компоненты и пресеты** — по потребности. Новый компонент лучше брать, когда его можно сразу проверить в плагине:
  непроверенное отображение в Figma превращается в долг.
- **Доступность** (#28) — до этапа 4: она меняет контракты, и дешевле внести её до генераторов.
- **Улучшения инструментов** (#37) — в любой момент.

## Открытые вопросы

- Вынос плагина Figma в отдельный репозиторий: нужен ли и когда.
- Kotlin Multiplatform для сгенерированного слоя — решается на этапе 4.
- Способ вести историю изменений контрактов — решается на этапе 1.

## Как обновляется

- `ROADMAP.md` меняется только через PR.
- Если задача меняет статус слоя в разделе «Где мы сейчас», таблица обновляется в том же PR (скилл `take`).
- Новая задача при груминге привязывается к вехе этапа или остаётся вне этапов (скилл `groom`).
- Этап закрывается по критерию завершения: веха закрывается, таблица обновляется.
- Смена видения, границ или порядка этапов — отдельный груминг.
